## 引き金索引——「こういう場面に出くわしたら、この節を引け」

> **使い方**：節を探すのではなく、**今おのれが置かれている場面**から引く。節の見出しを覚えて
> おらずとも、場面さえ思い当たれば辿り着けるように並べてある。
>
> **全節は載せていない**——**引き損ねると事故になるもの**に絞ってある。ここに無い節は、
> 本文を順に読めば足りるものと心得よ。
>
> **なぜ索引が要るか**（2026-07-27、殿ご下問への回答から）：本文を起動時に一度読んでも、
> **「読んだ」ことと「必要な瞬間に引ける」ことは別物**である。侍は同日、本節（ビルド検証）に
> 「App.Testsは未確認」と書かれていたにもかかわらず、**二度ロックに当たるまでそれを思い出せなかった**。
> 分量ではなく索引の問題であった。

### 問われた時・請われた時・**己の名が出た時**——**外から働きかけられた場面で引く**

> 引く契機が己の内側に無くとも発生する**。**ただし例外たりうるかは推測であり、実地で測る要あり。**

> **【この前書きが一度書き損じられた経緯】** 家老は当初、**例外（本区分は(c)に効く見込み）だけを単独で立て、

> 書いてあることを引く機会そのものが失われる。** ゆえに効果を測る際は
> **(a)引いて救われた (b)引いたが載っておらなんだ (c)そもそも引くことを思いつかなんだ**の

> **上の三分類は「引いたか否か」で切っておるが、引いた後にも穴がある。** 実例＝侍は
> 「発見を報じる時は限界（射程）も自分で区切る【MUST】」を**引いた上で守り、家老への報告では
> 留保を7件挙げた**。にもかかわらず**同じ日にテストのXMLコメントで射程を誇張した**——

**侍が偶奇という分類軸を持ち込み、その軸で説明しようとした**ことにござる。

**実例＝T-139。** 侍は枠`h/2`対可動`h-1`の関係を**「`h≧3`の奇数で枠外へ出る」**と書いた。
**実際は`h-1 > h/2 ⟺ h > 2`にて、`h≧3`のすべてで越える**（`h=4`なら枠`±2.0`に対し可動`±3`）。

**侍の弁＝「某は`h=2`で越えぬのを見て『偶数では越えぬ』と読み申した。
されど`h=2`が越えぬのは偶数だからではなく、境界だからにござる。
`h=4`を確かめておれば即座に露見しており申した」。**

**最も重いのは——侍のテストは`h=12`（偶数）を含んでおり、実装もテストも正しかった。
テスト名も「高さ3以上では」と正しく書かれておった。誤っておったのは、それを説明する計画書と
コミットメッセージの言葉のみ**にござる。**己の書いたテストと己の言葉が食い違うておるのに気づかなんだ。**
**なお家老もこの表現を確かめずに台帳・采配文へ二度引き写しており、捕らえたのは隠密の静的レビューであった。**

**How to apply**（侍の具申）
1. **「Aのときのみ B」と書いたら、Aでない場合を「境界と非境界の両方」確かめよ。**
   **侍が見たAでない場合は`h=2`の1つだけで、それが境界＝特異点であった。**
   - **【この項は一度誤った。侍の自己訂正 2026-07-31】** 初稿は**「2つ以上確かめよ」**であったが、
     **その「2つ」に根拠が無い**——**本件ではたまたま効く**（偶数のうち境界は`h=2`のみゆえ、
     2つ目で必ず非境界に当たる）**が、境界が2つ以上ある分類では、2つ見てもなお特異点ばかりを引きうる。**
   - **侍の弁＝「某は『2つ以上』という数の軸を持ち込み、その軸で手順を書き申した。
     されど真に効くのは『境界か否か』という性質の軸にござる。数ではなく性質の問題であった。
     軸を立てた瞬間が確かめ時——本項が説くとおりのことを、本項を書く段でまた繰り返し申した」**
   - **すなわち本項は、制度文を書く段でその制度文が説くことを破った実例を、自らの中に抱えておる。**
     **根拠なき数を制度文へ残せば、後から読む者が「なぜ2つか」と問うた時に答えられぬ**（侍の指摘）
2. **己の書いたテストが何を含んでおるかと、己の言葉が合うておるかを照らす。**
   **テストは`h=12`を含んでおったのに、言葉は「奇数」と言うておった**

**関連**＝上の子節が**「実測の外側へ出る言い回し」を合図**とするのに対し、本項は
**「分類軸を持ち込んだこと」自体を合図**とする。**偶奇・正負・大小・内外——軸を立てた瞬間が確かめ時。**

## 同値ガードは、比較する値の「型」まで見る【MUST】（2026-07-28、T-134往復1周目で侍が提起）

**「全フィールドを比較しておるか」を数えるだけでは足りぬ。一つ一つの型が `null` を取りうるかまで見よ。**

**実例**＝T-134で文書情報へ同値ガードを新設した。**8項目すべてを比較しており、数の上では漏れが無い**。
にもかかわらず、**`Date` だけが `string?` で新規文書では `null` から始まる**
（他7項目は `string` で既定 `""`）。一方ダイアログは `current.Date ?? ""` で表示し、OKで
`DateBox.Text` をそのまま返す——**何も触らずOKしただけで `""` が返る**。素の `==` では
`null != ""` ゆえガードを素通りし、空のスナップショットが積まれて**既存のRedo履歴まで消えた**
（忍者の実機確認で発覚）。

**なぜ文書情報だけが漏れたか**——同じT-134で加えた他2箇所（機器名 `el.DeviceName ?? ""`・
行コメント `existing?.Text ?? ""`）は**元から正規化されておった**。
**単一の値を取り出す形では `?? ""` を書く癖が働くが、8項目を一列に並べて比較する形では、
その中の1つだけが `string?` であるという事実が視界から落ちる。**
**「まとめて書く」ことそのものが、個々の性質を隠したのである。**

**How to apply**
1. **同値ガードを書いたら、比較しておる各値の宣言を見に行く**。`?` が付いておるものはないか
2. 付いておれば **`(a ?? "") == (b ?? "")` の形へ正規化する**——`null` と「空」がいずれも
   「未設定」を指すなら、同一視するのが意味論に適う
3. **ただし正規化が効きすぎておらぬかを逆側から押さえる**——実値のクリア（`"2026-07-28" → ""`）は
   依然として「変更」として検出されねばならぬ。**この逆側の網を必ずテストに置くこと**

**関連**＝直下「テスト入力の対称性・退化性チェック」の項目7（**同じ穴のテスト側**）。
**本節が実装側、あちらがテスト側で、一つの事象の表裏にござる。**

> **【Wチェックが効いた】本件は侍と隠密が独立に診断し、機序・対処案とも一致した**
> （材料は忍者の観測のみを渡し、互いの診断は渡さなんだ）。
> **なお隠密は先だって「同値ガードを見たら、比較しているフィールドが型の全フィールドか数える」
> という観点を挙げており、それは正しい場所を指しておった**——**穴は「数」ではなく「型」の側に
> あっただけである。一歩進めて『型まで見よ』としておれば、実機に出る前に届いていた。**

## テスト入力の対称性・退化性チェック（2026-07-25、PR-27候補。T-068増分3-b1で同一タスク内6件）

RED先行証明（上記）が「テストがバグを検出できるか」を問うのに対し、本節はさらに一段深い層——
**テストは在り、経路も通っているのに、与える入力値の選び方だけが原因で検出力を失う**罠を扱う。

**チェック項目**：テストの入力値が以下に該当する場合、そのテストは特定のバグを打ち消しうる。
- **対称な値**：`dx == dy`、正方形、原点中心、中心対称な図形、左右対称なUI状態、同一値の繰り返し
- **軸上・境界上の値**：`dy == 0`（X軸上）、`dx == 0`（Y軸上）、境界ちょうどの値
- **退化した値**：ゼロ、同一点、空、要素1個、**`null`**（**「空」とは別物**——`null != ""` にござる）
  - **【2026-07-28追加】退化入力のテストは、範囲の「外側」で測らねば検出力が出ぬ**——
    T-133増分4で侍が`Math.Max(0, cellHeight - 1)`の退化ガードを4箇所へ入れた際、**初版は行0で測っており、
    ガードの有無で結果が変わらなんだ**（`0-0>=0`も`0+1>=0`も真）。**緩みが現れるのは範囲の外側**にて、
    **行-1へ改めて初めて2件のREDを得た**。侍の弁＝**「『退化入力を測る』という見立ては正しく、境界の
    選び方だけが誤っておった。実測を通したゆえ露見した」**——**本節冒頭の「テストは在り、経路も通って
    おるのに、与える入力値の選び方だけが原因で検出力を失う」そのものにござる**
- **同一の実体**：**比較・同値判定を検証するテストで、両辺へ同じインスタンスを渡す**
  （**必ず一致するゆえ、判定の中身を一切検証できておらぬ**。詳細は下記 項目7）
- **仕様上の上限値**（2026-07-28追加）：型や設定が許す最大。**「まさかそこまで」で省かれがちだが、
  境界の外側ではなく**内側の端**ゆえ実際に到達しうる。実例＝P-148の`FrameRect`テストへ**高さ12**を入れた
  （原本GuiEcadの`HeightBox`が`Math.Clamp(..., 1, 12)`で許す上限。**上限値そのものは隠密の調査書から引いた**）

これらは**符号の反転・成分（X/Y）の取り違え・`&&`と`||`の取り違え**といったバグを、期待値と結果が
偶然一致することで隠してしまう。**対称性を崩した入力（非対角・軸外・非原点・非正方形）を1ケース
加えるだけで検出力が生まれる**。

**How to apply**：
1. テストを書いたら、入力値を眺めて上記に該当しないか確認する。該当するなら非対称な値へ置き換えるか、
   非対称ケースを追加する
2. 疑わしい箇所は**実装の該当ガード・符号・成分を一時的に壊してREDになるか実測する**（RED先行証明の
   手法をそのまま流用できる）。**手計算での検算**でもよい
3. **「期待値の直接検証ゆえ実装が誤れば必ず落ちる自明な形」という判断を、実測なしに下さない**——
   T-068増分3-b1では、まさにその「自明」と判断して実測を省いた群から4件の穴が見つかった
4. テストのコメントに「なぜこの入力値を選んだか（対称な値を避けた理由）」を書き添えておくと、
   次に触る者が同じ穴を掘り直さぬ
5. **【2026-07-27追加＝効果が数値で裏づけられた実例】T-125増分αで、本節の一般則を先回りして
   適用した結果が実測で出た**。グリッドを`Rows=5`・`Columns=10`と**非正方形**にしておいたゆえ、
   RED証明の改変B（行と列を取り違える）で**4件のRED**を得た——**正方形グリッドであれば0件、
   すなわちこの型のバグを丸ごと見逃していた**。同じく mm座標のX/Yに**異なる値**を与えておいたゆえ、
   改変C（Y軸を見ない）で**3件のRED**を得た。**本節はこれまで一般則と「穴が6件見つかった」という
   事後の数字しか持たなかったが、「非対称にしたから何件検出できた」という事前適用の数値実例が
   これで揃った**（侍の提起、2026-07-27）
6. **【2026-07-28追加＝2例目。事前適用が再現性を持つことが示された】T-134で、要素の座標を
   `GridPos(1,3)`と非対称にしておいたゆえ、`Pos`の行と列を入れ替える改変で14件のREDを得た**。
   T-125増分α（上記5）と併せ、**「非対称を選んだから何件検出できた」という事前適用の数値が
   2例揃うた**——**1例では偶然の余地が残るが、2例目で手立てとしての再現性が立つ**。
   - **併せて、着手時に非対称を選ぶ手は`[Theory]`の入力設計にも効く**。本件では境界値表を
     `(10,3)`（行が外）・`(1,20)`（列が外）と**行と列で別の値**にしたゆえ、どちらの軸の
     判定が壊れても別々のケースが落ちる形になった
   - **【射程を自ら区切る】測ったのは「行と列の取り違え」という単一の改変に対する検出力のみ**である。
     符号の反転・論理演算子の取り違え等、他の型については本件では測っておらぬ。
     また**「14件」という数はテスト総数（45件）に依存するゆえ、件数の多寡そのものに意味を
     持たせてはならぬ**——意味があるのは**「0件ではない」ことと、対称座標との対比**にある。
     さらに**「対称座標なら0件」は、入れ替えても同一セルを指すという構造から自明なのであって、
     テストを対称座標へ書き換えて実測したものではない**（侍の留保、2026-07-28）
7. **【2026-07-28追加＝退化の極みは「同一の実体を渡す」ことである】**
   **T-134の文書情報テストが実機の不具合を素通しした理由は、まさに入力値の退化にあった。**
   同値を検証するテストが **`vm.ApplyDocumentInfo(vm.Document.Info)` と同一のインスタンスを
   渡しており**、これでは**どう比較しても必ず一致する**——**同値ガードの中身を一切検証できておらぬ。**
   併せて、他の文書情報テストは `Date` に必ず非nullの値（`"2026-07-28"`）を渡しており、
   **`null` という退化値を一度も通しておらなんだ**。**実機の経路（新規文書＝`null` ＋
   ダイアログが返す `""`）は、テストの外にあった。**
   - **「同値を確かめるのだから同じものを渡せばよい」は自然な発想である。だからこそ罠**にござる。
     **同値ガードのテストでは「値は等しいが実体は別」の組を渡すこと。**
   - **【この項の立ち位置】上記1〜6（幾何演算の対称性）とは対象が違う**——
     **あちらは座標の対称、こちらは参照と `null`**。**されど「入力値の選び方だけで検出力が
     失われる」という機序は同一**ゆえ本節に置く（侍の判断）
   - **関連**＝直上の節「**同値ガードは、比較する値の『型』まで見る**」（**同じ穴の実装側**）

**Why**: T-068増分3-b1（2026-07-25）で、幾何演算の新規テスト群から同型の穴が**同一タスク内で6件**
見つかった。侍がRED証明の代替実測中に1件（矩形が中心対称ゆえ回転の符号を反転させてもGREENのまま）、
隠密の静的レビューが1件（`RotatePoint`の2テストがいずれも`dy=0`または`dx=dy=0`の退化入力ゆえY成分の
符号検証が丸ごと消えていた）、家老が「同型2件目ゆえ3件目を疑うのが筋」と拾って1件、**さらに侍が
自ら洗い直して3件**。補強後の実測では`RotatePoint`のdy符号反転で**補強前は間接テスト1件のみRED→
補強後は7件RED**となり、穴の実在が数字で裏づけられた。侍の所感——**「『自明ゆえ実測を省く』という
判断そのものが穴の温床であった」**。

なお本パターンは幾何演算に限らない。「入力値の対称性・退化性がバグを打ち消す」という一般則ゆえ、
対称な設定値・左右対称なUI状態・往復変換（encode/decode、シリアライズ/デシリアライズ）等でも
同型が起こりうる。詳細は`docs-notes/pattern-recurrence-log.md` PR-27候補。

**【最重要の補足】見立てを述べることと、それを入力値に落とし込むことは別物**（2026-07-25、同日中に
本節が制度化された直後の実例）。同じT-068増分3-b3で、侍は`MergeCollinearLines`のテストを書くにあたり
**自ら「端点一致の判定・平行判定の外積が対称・退化入力で検出力を失いやすい」と正しく見立てていた**。
にもかかわらず、いざ書いたテストで`&&`を`||`へ取り違える実測を行うと**全件GREEN＝検出力なし**——
「X座標だけ一致してY座標が離れている」端点の組み合わせが一つも無く、既存ケースはいずれも**両軸とも
一致か、両軸とも離れているか**のどちらかだったため。X座標のみ一致・Y座標のみ一致の2ケースを補い、
2件REDを実測して塞いだ。侍の所感——**「見立てを述べることと、それを実際の入力値に落とし込むことは
別物と思い知った」**。

**ゆえに**：本節を読んで「心得た」と思っても、それだけでは穴は塞がらぬ。**必ず「壊す実測」という
機械的手段を通すこと**。パターンを知っている者ですら自分のテストには適用しきれぬ、というのが本節の
最も重要な教訓である。逆に言えば、実測さえ通せばパターンを知らずとも穴は見つかる。

なお同じ実測で、外積の符号取り違えが**9件RED**になったのは侍が**斜め線を選んだ効果**であった——
水平・垂直では方向ベクトルの片方の成分が0になり、この取り違えは結果に現れない。上記チェック項目の
「軸上・境界上の値」がそのまま効いた実例である。

**【事前に効いた実例】本節を読んだうえで着手すれば、穴は掘らずに済む**（2026-07-25、同日のT-068
増分3-c）。上記の補足で「見立てを入力値に落とし込むのは別物」と痛感した侍は、続く増分3-cで
**着手の時点で**「接続点のxは`BoundaryOffset`、yは`RowOffset`で、`PortDef`の宣言順とは逆」という
取り違えやすさに気づき、**テストの入力値に非対称な位置`(行1,境界4)`をあらかじめ選んでおいた**。
結果、実測でも穴は出ず「3度目は掘らずに済んだ」。同じ増分で`ClampPort`の行上限から`-1`を落とす実測
では**「高さ1のときRowOffsetは0のみ」という退化ケース2件がRED**になっており、境界・退化入力を意識
して選んだテストがそのまま検出力を持った。

**つまり本節の使い方は2段構えである**：(1)**着手時**——実装のどこに符号・成分・論理演算子の取り違え
が潜みうるかを見立て、**その見立てをテストの入力値へ落とし込む**（対称・軸上・退化を避ける）
(2)**実装後**——それでも「壊す実測」を通す（見立ては漏れうるため）。1だけでは3-b3の轍を踏み、2だけ
では手戻りが増える。

**【重要な留保】上記の「事前に効いた実例」を過大に読まぬこと**（2026-07-25、侍自身の戒めによる）。
家老は当初これを「制度が事前に効いた初の実例」と評したが、侍は**自らその評価を差し戻した**——
> こたび気づけた直接の因は`PortDef`の宣言順と座標の対応が逆転しているという、**目に見えて明白な罠**
> だった。3-b1の「矩形が中心対称ゆえ符号が消える」・3-b3の「両軸とも一致か両軸とも離れているかしか
> ない」のような**見えにくい型**が次に現れたとき、同じように気づける保証はない。**「3度目は掘らずに
> 済んだ」を「以後も掘らずに済む」と読まぬよう己を戒めている。制度の要は依然「壊す実測」という
> 機械的手段にある**

**この留保を制度の一部として残す。** 着手時の見立て（段構えの1）は**当たれば手戻りが減るという程度の
もの**であり、**検出力を保証するのは実測（2）だけである**。1が効いた経験を積んでも2を省いてはならぬ。

### 【別軸】本数・件数を測るテストは、位置の誤りを検出せぬ（2026-07-31、T-137で侍が提起）

**上記の節が「与える入力値の選び方」の軸であるのに対し、本項は「何を測るか＝アサーションの対象」の軸**
にござる。**入力を非対称に選んでも、測る量が集約値であれば、その集約が潰した情報の誤りは通り抜ける。**

**実例＝T-137（パーツエディタの区切り線）、侍の壊す実測より。**
**改変A（横線のy座標から`+0.5`を落として整数へ＝縦線との区別が消える）で7件のREDを得たが、
本数を測る`GridLineYs_枠の範囲では高さの2倍の本数になる`はGREENのまま**であった
——**半整数を整数へ動かしても本数は変わらぬ**ゆえ。

**【両軸は一度の実測で同時に現れうる】** 同じ壊す実測で、**上の既存節の型（入力値の選び方）も併せて
現れた**——**改変B（範囲の切り出し誤り）で落ちなんだ`GridLineXs_幅3の枠では整数の位置に入る`は、
位置を直に測るテストにて集約値ではない。通り抜けた因は、渡した範囲が整数ちょうど（0.0〜3.0）で
あったこと**にござる。**すなわち本節ではなく既存節の実例。** **一度の実測で両軸の穴が同時に露見しうる
ゆえ、落ちなんだテストを見つけたら「集約ゆえか、入力ゆえか」を分けて問え。**

**How to apply**：本数・件数・合計といった**集約値**を測るテストを書いたら、**その集約が何を潰すかを問う**。
**本数は位置を潰し、合計は分布を潰す。** **集約値のテストは「在ること」の網であって「正しく在ること」の
網ではない**——**位置・内容を直に測るテストを別に置く。**

**【射程を区切る】侍が実際に観測したのは、改変Aにおいて集約値を測るテストがGREENのまま残った、
という事実1件のみ**にござる。**「集約値のテストが常に位置の誤りを逃す」ことまでは測っておらぬ。**
**なお本節の初版は改変Bをも本節の実例として並べておったが、これは家老の読み違いにて、
侍の検分で正した**——**発生源は侍の報告文が両者を「同じく」と並べたことにあるが、
それを検めず書いたのは家老の落度にござる。**
**また本項も、検出力を保証するのは上記の節と同じく「壊す実測」だけである**——
**本項は実測の結果を読む際の着眼であって、実測に代わるものではない。**

## 裁定そのものでなく、裁定の「根拠」を回帰テストの対象にする【MUST】（2026-07-28、P-148で侍が提起）

**殿の裁定は、家老が差し上げた材料の上に下される。**
**その材料が将来崩れても、裁定の文言だけは残る**——**ゆえに材料の側をテストで固定せよ。**

**実例**＝P-148（基準枠の行範囲）で、殿は**「既存18件への影響なし（組込み15件は高さ1）」**という
材料をご覧になって案(b)を裁可された。侍は実装後、
**`FrameRect_HeightOne_P148の前後で変わらない`**というテストを置いた——
**将来この式から `+0.5` を落とす変更が入れば、このテストが鳴る。**

**実効性は同じ日に裏づけられた**——**家老が殿へ諮った当初の案（素直な `±(h-1)`）では、
まさにこの前提が崩れていた**（高さ1で枠が `±0` となり組込み15件すべてで枠が消える）。
侍が着手前に気づいて差し戻し、殿の再裁定を仰いだ。
**すなわちこの前提は「崩れうる」ことが実証済みである。**

**How to apply**
1. **裁定を受け取ったら、「何を材料に選ばれたか」を書き出す**——「影響なし」「実害が小さい」
   「既存と揃う」等。**それらは事実の主張であり、コードが変われば崩れうる**
2. **崩れたら鳴るテストを1つ置く。** テスト名に**裁定の名（P-148 等）を入れておく**と、
   将来鳴った時に「なぜこの値でなければならぬか」が辿れる
3. **改変で鳴らぬことが正しいテストもある**——本件の当該テストは、
   裁定の前後で値が変わらぬことを固定する網ゆえ、**その改変では鳴らぬのが正しい**。
   **完了報告では「鳴らぬのが正しい」と自ら名指しすること**（下記「RED先行証明」の作法）

**既存節との違い**：上の「テスト入力の対称性・退化性チェック」は**バグを検出できるか**を問い、
本節は**仕様判断の前提が保たれておるか**を問う。**前者は実装の誤り、後者は前提の風化を捕らえる。**

## テスト設計と実装の分離【MUST】（バグ修正・往復案件、2026-07-08殿裁定）

バグ修正・修正往復が発生した案件では、隠密が仕様側から起草した**テスト設計書**（`onmitsu.md`「テスト設計の起草」参照）に従ってテストを実装する：

- 設計書に挙がった観点・経路・アサーション・境界値は**すべて**実装する（勝手に省かない。省くべきと考えたら家老へ差し戻す）
- 設計書にないテストの追加は自由
- 同じ検証ロジックで入力だけ変わるケース群は`[Fact]`の複製ではなく`[Theory]`+`[InlineData]`で書く（境界値の網羅を間引かないため）
- 通常の新規実装（バグ修正でないもの）は現行どおり自分でテストも書くが、上記`[Theory]`活用と境界値分析（下限-1/下限/上限/上限+1）の適用は同様に心がける

**Why**: 実装した本人がテストを書くと、仕様の誤解がテストにそのまま写る（実装者バイアス）。設計と実装を別人格に分けることで仕様の解釈が2系統になり、T-041増分7で起きた「旧実装でも新実装でも通るテスト」の再発を構造的に防ぐ。

### 設計書と裁定が食い違ったら、裁定側へ寄せて「寄せた」と明示する（2026-07-28、T-125β-1実害修正の実例）

**隠密のテスト設計書と、家老の采配・殿の裁定が食い違う場面が実際に起きる。**
実例＝設計書のS-4は「**排他規約を手放してはならぬ**」と定めたが、家老のスコープ境界は
「**両立状態（P-142）には触れぬ。γの領分と結論済み**」であった。**採った案では前者を満たせぬ。**

**作法＝裁定側へ寄せる。ただし「寄せた」ことを完了報告に明示する。**
**黙って寄せれば、後から設計書を読む者はそれを現行仕様と信じて混乱する。**

## 【チェックリスト群の前に】横展開の漏れは、機械に検出させられぬか先に問う【MUST】（2026-07-28、T-133増分3で侍が提起）

**以下に続くチェックリスト群は、いずれも「人が点検する」形にござる。**
**されど漏れの中には、型で防げるものがある**——**そちらが先である。**
**チェックリストが要るのは、機械に検出させられぬ時だけと心得よ。**

**同じ日に、侍は両方をやっておる。その対比が本節の眼目にござる。**

| | 増分2（人の点検） | 増分3（機械の点検） |
|---|---|---|
| 為したこと | `CellWidth` を書いておる**全箇所を機械的に列挙し、`CellHeight` を並べたか照合**した | `cellHeight` を**必須引数（既定値なし）**とした |
| 漏れの防ぎ方 | **侍が数え、隠密が数え、突き合わせた** | **コンパイラが全呼び出し元を洗い出す。漏れれば通らぬ** |
| 限界 | **数え落とせば漏れる。**「production 3箇所」という数自体、前任の調査書が1件誤っておった | **既定値を付けた瞬間に効かなくなる**（ラッパー2件は既定1ゆえ、そちらは人の点検に戻る） |

**How to apply**：新しい引数・新しい状態を足すとき、**既定値を付けるか否かを「改修の手間」で決めるな。**
**「漏れを検出できるか」で決めよ。**
- **既定値なし（必須）** → 呼び出し元すべてに手が入るが、**渡し忘れが原理的に起き得ぬ**
- **既定値あり** → 既存は無改修で済むが、**渡すべき所で渡し忘れても黙って通る**

**本件では「4メソッドは必須／公開ラッパー2件のみ既定1」と切り分けた**——
**ラッパーは View 層の3呼び出しを無改修に留めるため**（範囲を広げぬ判断）。
**すなわち一つのタスクの中でも、箇所ごとに使い分けてよい。**

> **【留保】これは「チェックリストが不要になった」という話ではない。**
> **型で防げるのは「渡し忘れ」までであり、「渡した値が正しいか」は防げぬ。**
> 実例＝増分3で `PlaceElementAtSelectedCell` へ `cellHeight: 1` と明示したが、
> **これが正しいのは「増分4までは高さを持つ要素が置かれぬ」という前提あってのこと**にて、
> **その前提はコンパイラには見えぬ**（docコメントと下記チェックリストが受け持つ）。

## SetProperty早期return罠の確認（2026-07-13、隠密2棚卸しでPR-03確定）

`SetProperty`（値が変化した場合のみ`OnPropertyChanged`を発火し、変化なしなら早期returnするヘルパー）を
使うプロパティで、**セットする値が「実体の変化」を必ずしも表さない場合**（例：`CurrentSheetIndex`のような
添字/インデックス値。シート削除・並べ替え等で参照先の実体は変わったが、添字自体は偶然同じ値に戻る）、
早期returnにより本来発火すべき`OnPropertyChanged`とそれに連鎖するクリア・再描画処理が丸ごとスキップ
される。T-019・T-041増分5・T-082の3タスクで独立に再発した（`docs-notes/pattern-recurrence-log.md`PR-03）。

新しいプロパティに`SetProperty`を使う際、値が「一意な実体」ではなく「添字/インデックス/数値キー」等、
偶然一致しうる値の場合は、値の一致だけで処理をスキップしてよいか（実体側の変化を見逃さないか）を
自己点検する。

## 新規プリミティブ・座標処理の境界検証チェックリスト（2026-07-13、隠密2棚卸しでPR-04確定）

新しい図形要素・配置操作・座標を扱う処理を追加する際、既存要素（Grid行数範囲・画面外周・ページ境界・
min>maxガード等）で確立済みの境界クランプ・範囲検証パターンが、その新規実装には移植されずクラッシュ・
視覚異常・はみ出しを招く再発が繰り返されている（T-033・T-041増分7・T-051・T-055増分1の4タスク、
台帳中最多の再発件数）。

新しい座標処理・図形要素を追加する実装では、着手前に以下を自己点検する：
0. **【2026-07-27追加・最重要】そのガードは「入力の出所」に合った尺度で書かれておるか**——
   **同じ式でも、入力がどこから来るかで守るものが変わる。** 実例＝T-125増分αで、接続点・自由線の
   ガードに原本GuiEcadの`xMm >= 0`（mm下限）をそのまま借りたが、**原本の入力はマウス座標**ゆえ
   「キャンバス外を指した場合の無視」として機能するのに対し、**ecad2の入力は`SelectedCell`**で
   あり`MarginMm`を挟む変換を経る。ゆえに**範囲外セル（行`-1`・列`-2`）でもmm座標が正になり
   （列-2でX=2.0、行-1でY=15.5）、ガードが常に素通り**した。侍の自省＝**「計画書で『操作方式が
   原本とecad2で根本的に異なる』と自ら書いておきながら、ガードの尺度は原本からそのまま借りた」**。
   **正解は「起点はグリッド内（GridPos の尺度で判定）、伸びる先・移動先は自由（mm の尺度）」**——
   **判定は変換の手前で行う**のが筋。
   - **併せて、テストは必ず変換を通した形で書く**——当時のテストは`PlaceConnectionDot(-0.1, 33.0)`と
     **mm座標を直接渡しており、セル→mm変換を一度も通しておらなんだ**。**変換の後の値でいくら境界を
     刻んでも、変換そのものが持つズレは永久に現れぬ。** 修正時のRED証明では、起点セルのガードを
     除去しても**旧テスト12件は全件GREENのまま**であった＝**旧テストでは検出できなかったことの実測**
   - **効果測定の指標も同じ**——「境界ガードを**持つ**数」では嘘をつく。**「入力の出所に合った尺度の**
     **境界ガードを持つ数」**で数えねばならぬ（初版は9/9と数えたが実は7/9であった）
   - **【付随して判明したC#の罠】`readonly struct`で宣言した既定引数は、パラメータレス生成では
     効かぬ**——`GridGeometry(double cellMm = 9.0, double marginMm = 15.0)`と書いても、
     **`new GridGeometry()`では暗黙のパラメータレスコンストラクタが選ばれ全メンバーが既定値
     （`MarginMm = 0`）になる**。宣言した既定値は**引数を1つ以上渡した時のみ有効**。
     **「コンストラクタの既定値はこうだから」という読み方自体が、書き方次第で成り立たぬ。**
     加えて本件では、その既定値15.0は`DiagramRenderer.cs:44`が`RenderOptions.MarginMm`（既定20.0）
     で上書きしており、**そもそも実行時には使われておらなんだ**——**既定値は「宣言」でなく
     「実際に構築される経路」を辿って確かめよ**
1. 既存の類似要素（コネクタ・要素・画像等）が持つ境界クランプ処理と同等のガードを新規実装にも適用したか
2. Grid行数・列数の範囲外アクセスにならないか（下限-1/下限/上限/上限+1の境界値で確認）
3. 画面外周・ページ境界を超えないか
4. min>maxとなる縮退ケースのガードがあるか
   - **【2026-07-28追加】式を変えると、退化入力の扱いが黙って変わる。** 既存の式が退化入力で
     たまたま無害だったからといって、新しい式でも無害とは限らぬ。**式を書き換えたら、退化入力を
     もう一度通せ。** 実例＝P-148で基準枠の半径を `±h/2` から `±((h-1)+0.5)` へ改めたところ、
     **高さ0で半径が負になり矩形が反転する**——旧式では高さ0＝半径0（無害）であった。
     `ClampPort` の `rowLimit` と同じく `Math.Max(0, ...)` で0段へ潰して塞いだ。
     **既存テスト（高さ0の退化ケース）が期待値の変更を要求したことで露見した**——
     **退化ケースのテストを置いておいたことが、式の変更時に効いた**
5. **【2026-07-25追加】既存の別経路への適用漏れも見る**——上記1〜4は「**新規に追加する時**」を
   想定したチェックだが、「**既存の別経路に、後から責務が生まれた**」場合が死角になる。同じ値を
   書き換えうる全経路（プロパティsetter・サイズ変更・一括操作・復元処理等）を洗い出すこと。
   実例＝T-068増分3-cで、ポートのクランプが「新規追加」「ドラッグ移動」の2経路にのみ実装され、
   **「基準枠のサイズ変更」という3つ目の経路が漏れていた**（`memory:
   feedback_checklist_layer_mismatch_blindspot`＝チェックリストのレイヤー不一致による死角と同型）。
6. **【2026-07-25追加・最重要】「漏れ」と断ずる前に、それが意図的な不在かを確かめる**——
   既存コードに処理が「無い」ことを欠落と決めつけてはならぬ。**とりわけ「GuiEcad踏襲」で作った
   箇所に手を入れる時は、原本にその処理があるかを必ず見る**。
   実例＝上記T-068増分3-cの「漏れ」は、**原本を確かめたところ原本自身がクランプしておらず、
   「欠陥」という前提自体が誤りであった**（クランプを足す修正は踏襲方針からの逸脱の追加であり、
   さらにUndo復元時の中間状態という別の欠陥まで生んだ）。侍の総括＝**「踏襲したはずのものに
   *無い*処理を『バグ修正』として足そうとしておる。これは筋が通らぬ」**。
   **`memory: feedback_verify_design_intent_before_quickfix`の「一次ソース」は、自プロジェクトの
   コード・コメントだけでなく踏襲元の原本まで含むと読むこと**（コメントや自プロジェクトの一次
   ソースを読むだけでは足りなかった、というのが本件の教訓）。
   **【2026-07-27追記＝「漏れ」と「意図的な不在」は同一タスク内で混在しうる】経路ごとに個別に
   確かめよ。種別が違えば結論も違う。** 実例＝T-125増分αで、**配線分断は原本に同型ガードがあり
   「実装漏れ」、接続点・自由線は原本にも上限が無く「意図的な不在」**であった（mm実座標はグリッド外へ
   広がる設計で、レンダラにも前提が明記されておった）。**上記T-068の実例は「全部が意図的だった」型
   ゆえ、混在しうることが書かれておらなんだ。「原本を見た→無かった→ゆえに不要」で止めておれば、
   今回は配線分断の漏れを取りこぼしていた**（侍の提起）。

## 「テストしにくい」は設計の匂い（2026-07-25、T-068増分3-cの実体験より侍が提起）

**「View層ゆえ単体テスト困難」と判じた時、まず「設計を変えれば純粋関数にできぬか」を問うこと。**
テストのために特殊な仕掛け（STAスレッド包み込み等）を用意するのは**最後の手段**とする。

**実例**：T-068増分3-cで`PartEditorCanvas`のsetterへ処理を入れた際、`FrameworkElement`派生ゆえ
単体テスト困難と判じ、**専用STAスレッドで包む手法を編み出して4件のテストを実現した**
（本プロジェクト初）。ところが殿の裁定で「保存時のみ適用」へ設計が変わった途端、同じ処理が
**Core層の純粋関数となりテストは8件へ倍増、壊す実測で3観点の検出力まで確かめられた**。
侍の総括＝**「STAで包んでいた頃より遥かに堅い。『テストしにくい』は設計の匂いであった」**。

**STAスレッド包み込みの勘所**（それでも必要になった時のために記す）：`FrameworkElement`派生は
コンストラクタで`InputManager`を初期化するためMTAでは即例外。`Thread.SetApartmentState(STA)`＋
`Join`で同期実行する。**例外は必ずキャプチャして再throwすること**——握り潰すと全件GREENに見える。

### 【もう一つの向き】公開ラッパーを足すか否かは、テスト可能性で決まることがある（2026-07-28、T-133増分3）

**本節はここまで「private を純粋関数へ切り出す」向きを述べておるが、
「private のまま、公開ラッパーの側に引数を通す」という手もある。**

**実例**＝T-133増分3で `IsWithinGridBounds` / `IsOccupied`（いずれも `private static`）へ高さを通した。
**この2つには View 層向けの公開ラッパーが1つずつ在り**、隠密は調査で

**侍はラッパーにも通す方を採った。決め手は設計の美しさではなく、テスト可能性である**——
**ラッパーに通さねば、この2メソッドを直接検証する手立てが無かった**（配置経路を丸ごと動かす
間接テストしか書けず、判定そのものの境界を刻めぬ）。**結果、新規26件のうち大半が
ラッパー経由で書けた。**

**How to apply**：private なロジックへ手を入れる時、**「公開面のどこかに、その引数を通せる入口は
無いか」を問う**。**既定値を付けておけば既存の呼び出しは無改修で済む**ゆえ、
**テスト可能性を得る代償が小さい場合がある**。
**ただし「呼ばれぬ引数」を足すことになるゆえ、`docs/proposed.md` P-143（型はあるが結線が無い）を
新たに作らぬよう、結線先をdocコメントへ先に書き留めること。**

## ループ処理の終了保証チェックリスト（2026-07-21、T-077増分5実例）

行単位の反復処理（Markdown変換等）へ新しい除外条件・スキップ条件を追加する際、「その条件が
ループの最初の要素（1行目等）にも該当しうるか」を見落とすと、ループ変数が一切進まず無限ループ
に陥る。表構文判定の追加時、区切り線を伴わない`|`始まり行が新規除外条件と噛み合い、対象行が
一つも消費されないまま外側ループが停止するバグを作り込んだ実例がある（実装中に自己発見・
RED証明つきで修正、ガードを外すと実測でテストプロセスがハングした）。

新しい除外・スキップ条件をループへ追加する実装では、着手前に以下を自己点検する：
1. 追加する条件は、ループの最初の要素（未処理の先頭行等）にも該当しうるか
2. 該当しうる場合、その要素は無条件で最低1つ消費されてからループ変数が進む設計になっているか
3. 疑わしい場合は、タイムアウト付きで実測しハングしないことを確認する（RED証明の一環として）

## WPF「値は正しいが描画に反映されない」系の調査（2026-07-16、T-083実例）

プロパティ値をC#側で読むと正しいのに画面描画に反映されない、という症状に遭遇したら、
`System.Windows.DependencyPropertyHelper.GetValueSource(element, property)`で値解決経路
（Local/Style/Template/ParentTemplate/Inherited等）を確認するのが近道。AvalonDockドッキング
クローム・Menuドロップダウン背景の2件で、この手法により「TemplateBinding経由で親要素の値を
参照している」構造を素早く特定できた。原因特定後の対処（ControlTemplate自体の書き換え等）は
別途コスト評価が必要——構造特定が早くても、対処自体が大掛かりになるケースがある点は留意。

**PR-20確定（2026-07-18、3例判明）**：本症状は原因メカニズムが3系統に類型化できると判明
（`docs-notes/pattern-recurrence-log.md` PR-20参照）——(1)StaticResourceの固定解決（増分7
`SubMenuBorder`、DynamicResourceオーバーライドが原理的に届かない） (2)ItemsHostパネルの
コンテナ生成前提（T-099、Collapsed化がMeasure()を早期returnさせコンテナ生成自体を永久ブロック）
(3)**ControlTemplate.Triggersの依存関係プロパティ優先順位**（T-089、`Style.Triggers`での
Setter[優先度6位]が既定テンプレート内`ControlTemplate.Triggers`のSetter[`TargetName`指定、
優先度4位]に上回られ完全に握り潰される。WPF公式ドキュメント「依存関係プロパティ値の優先順位」
参照）。**予防チェックリスト**——既存の名前付きコントロール（Button/ToggleButton等）へ新規の
`Style.Triggers`（IsPressed/IsMouseOver等）を追加する際は、そのコントロールの既定
ControlTemplate（Aero2テーマ等）内`ControlTemplate.Triggers`に同一プロパティへの競合Setterが
既に存在しないか事前確認する（存在すれば優先順位で必ず負ける）。存在する場合はStyle.Triggersでの
上書きを諦め、ControlTemplate自体を部分自作（対象TargetNameのSetterを差し替え）する方針に
最初から倒すこと。

**PR-21確定（2026-07-19、2件目判明・本節の教訓記載後に再発）**：既定テーマスタイルを暗黙的/名前付き
スタイルで丸ごと置き換える場合、ControlTemplate（見た目の骨格）だけでなく、対応するStyle本体の
既定値Setter群（Background/BorderBrush/Foreground/BorderThickness/Padding等）も必ず一緒に移植
すること。ControlTemplate.Triggers内のStaticResource参照は**遅延解決**のためビルド時・XAML解析時
にはエラーにならず、実行時にトリガーが発火した瞬間`UnsetValue`として現れる——T-089でこれを見落とし、
**特定のトリガーに依らず**Style本体の既定値欠落によりTemplateBinding経由で通常のArrangeパスで

## 複数箇所を一括編集したら、コミットを待たず行数を照合する【MUST】（2026-07-27、P-141のヒヤリ）

**既存の作法は「コミット直後に`git show --stat HEAD`で想定行数と照合」だが、編集の段階にも同じ検算が要る。**

**実例**：P-141で`MainWindow.xaml.cs`の**9箇所を並列`Edit`した**。全て成功したが、
**`old_string`が一意でなければ誤爆する恐れがあった**。**安心できたのは差分-31行を照合してからである。**

**How to apply**：複数箇所を一括で編集した直後、**`git diff --numstat -- <path>`で行数を確かめる**。
**想定と食い違えば、その場で気づける**——コミットまで待つと、他の変更と混ざって切り分けが難しくなる。

### 「コメントのみの変更」は目視でなく機械で裏付ける（2026-07-28、侍が同日2度用いた）

コメントだけを直したつもりでも、**「つもり」を報告に書いてはならぬ。**

```powershell
git diff -U0 -- <path> | Select-String -Pattern '^[+-]' |
  Where-Object { $_ -notmatch '^[+-]{3}' } |           # ---/+++ のヘッダを除く
  Where-Object { $_ -notmatch '^\s*[+-]\s*(///|//)' }  # コメント行を除く
# 出力が空なら、変更はコメント行のみ
```

**実例**＝T-125β-1実害修正で既存テストのコメントを2度直した際、いずれもこの形で
**コード行の変更ゼロを確かめてから報告した**（家老の評＝**「機械的に確認したのが良い」**）。
**上記の`--numstat`による行数照合と併せて使えば、「何行変わったか」と「何が変わったか」の
両方が押さえられる。**

**併せて`Measure-Object -Line`の癖に注意**——**空行を数えぬ**。`git show HEAD:<path>`の出力を
これで数えると実ファイルの行数と食い違い、**「HEADが変わったか」と無用に疑う**羽目になる
（侍が実際に一度疑った）。**空行込みで数えるなら`(Get-Content <path>).Count`を使う。**

### 【重要】pathspec付きgit commitの罠（2026-07-18、同日2回再発）

`git commit -m "..." -- <pathspec>`は、**ステージング内容ではなくワーキングツリーの現在値**を
