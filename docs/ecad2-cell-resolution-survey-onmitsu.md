# パーツエディタのセル内分解能調査

隠密（key=1785485896132）記す。2026-07-31。家老采配より（DoD1改訂版を含む）。

## 0. 題目・スコープ

殿ご下問＝「セル内の分解能はどれくらいか。マウスで狙った位置になかなか置けない。1セルを4×4に割った位置でポイントできればいい」。**調査のみ・実装せぬ。刻み値の確定は殿の裁可を要す。**

**先に結論**——**現状は「1辺を16等分（線形）」であり、1セル内にポイントできる位置は縦横とも16×16＝256点。殿の御要望「1セルを4×4＝16点」との間には実在する差があり、現状は要望よりも4倍細かい（1辺あたり）。「記録の齟齬で16分割(4×4)と16分の1(線形)を取り違えたのでは」という殿のご懸念は、一次ソースを見る限り該当せぬ——コードは疑いなく「線形の1/16」であった。**

## 1. DoD1（改訂）：刻みの単位を一次ソースで確定する

### 1-1. 定数と関数の実物

`src\Ecad2.Core\Model\PartShapeGeometry.cs:18, 32-33`：

```csharp
public const double DefaultSnapFractionCells = 1.0 / 16.0;
...
/// <summary>座標値を刻み幅の倍数へ丸める。</summary>
public static double Snap(double value, double fractionCells = DefaultSnapFractionCells)
    => Math.Round(value / fractionCells) * fractionCells;
```

**`Snap`は`double`ひとつ（`value`）を受け取り、その1個のスカラー値を`fractionCells`の倍数へ丸めるだけの、疑いなく1次元(線形)の関数**である。2次元の面積・格子点を直接返す作りにはなっていない。

### 1-2. X・Yへの適用のされ方

`src\Ecad2.App\Views\PartEditorCanvas.cs:228`：

```csharp
private static Point2D SnapCell(Point2D p) => new(PartShapeGeometry.Snap(p.X), PartShapeGeometry.Snap(p.Y));
```

**`Snap(p.X)`と`Snap(p.Y)`を独立に2回呼んでいる**——Xの丸めとYの丸めは互いに無関係。**ゆえに「1辺を16等分」を縦・横それぞれに独立して適用しており、1セルの中にポイントできる位置は`16×16＝256点`（碁盤目状）になる。**

### 1-3. 「16分割＝4×4」という読みが成り立たぬ理由

もし「1/16」が**面積の分割**（1セルを16個の小マスに分ける＝縦横それぞれ4等分）を意味するなら、実装は「1辺を4等分した格子点」へ丸める形（`fractionCells = 1.0/4.0`を使うか、面積ベースの別の丸め処理）になっているはずだが、**そのような面積ベースの丸め処理はコード中に存在せず**、`Snap`は終始スカラー1個を線形に丸めるのみであった。**呼び出し元（`SnapCell`）もXとYを独立に2回呼ぶ形であり、「1回の呼び出しで面を16分割する」という構造は取っていない。**

**→ DoD1の答え**：
1. **1辺を何等分するか＝16等分**（線形、`fractionCells=1/16`）
2. **1セル内にポイントできる位置＝縦横16×16＝256点**
3. **縦横で異なるか＝異ならぬ**（`Snap(p.X)`・`Snap(p.Y)`とも同じ既定値`1/16`を使う、対称）

**殿の御要望「1辺を4等分＝1セルに16点」との差**＝**実在する。現状(256点/セル)は要望(16点/セル)より1辺あたり4倍・面積換算で16倍細かい。** ゆえに「差が無ければ他の原因を探す」という家老の分岐は不要——**差は明確にあり、現状の分解能の細かさそのものが、狙った位置に置きにくいという訴えの原因として十分に符合する**（マウスの手ぶれに対し、256点/セルは1点あたりの間隔が非常に狭い）。

## 3. 1/4刻みへ変えた際の影響範囲

### 3-1. 既存の1/16刻みで保存された部品データはどうなるか——**そのまま残る。丸められて動かぬ**

`PartLine`等のプリミティブは`double`型の座標をそのまま保持するだけで、量子化のための別途のインデックス・分母は持たない（`PartDefinition.cs:33-42`）。**永続化層（`Grep "PartShapeGeometry.Snap(" src/Ecad2.Core/Persistence/` → 0件）にも`Snap`の呼び出しは無く、読み込み時に座標を再量子化する処理は存在しない。** ゆえに`fractionCells`を`1/16`から`1/4`へ変えても、**既に保存済みの`double`値はファイルを開いた時点では一切変化しない**。

**では既存図形を後から動かした（移動ドラッグ）場合はどうか——動かしても、その頂点が新しい1/4格子へ強制的に吸着されることはない。** 理由は移動の実装にある（`PartEditorCanvas.cs:489-495` `UpdateMoveDrag`）：

```csharp
double dx = cell.X - start.X, dy = cell.Y - start.Y;
_primitives[_selectedIndex] = PartShapeGeometry.Translate(_moveDragOriginal, dx, dy);
```

**移動は「開始セルと現在セルの差分(`dx`,`dy`)」を元の座標へ加算する形**であり、元の座標そのものを新しい格子へ丸め直す処理ではない。差分`dx`,`dy`は（開始・現在ともスナップ済みゆえ）新しい刻みの倍数になるが、**元の座標が1/4格子に乗っていなければ、移動後も同じ端数（例：元が`0.3125`＝1/16刻みの半端な値なら、移動後も`0.3125 + (1/4の倍数)`のまま）がそのまま残る**。**すなわち「量子化のずれ」は移動によっても解消されず、そのまま引き継がれる。**

**新規に描く図形（線・矩形・円・弧・文字の新規配置）は、刻みを変えた瞬間から新しい1/4格子上の座標で作られる**——これは当然の帰結である。

### 3-2. 分解能が効く箇所はスナップだけか

家老指定の代表例に沿って確認した。

| 観点 | 影響の有無 |
|---|---|
| **当たり判定**（`PartShapeGeometry.cs:21` `DefaultHitToleranceCells=0.3`、`HitTest`等） | **影響なし**。ヒット許容距離は独立の定数であり、スナップ刻みとは無関係 |
| **保存形式** | **影響なし**。`double`座標をそのまま保存するのみで、刻み値自体を記録する項目は無い（3-1のとおり） |
| **描画** | **影響なし**。描画は保存済みの`double`座標を`CellMm`倍して描くのみで、`DefaultSnapFractionCells`を参照する箇所は描画コードに無い |
| **回転スナップ** | **無関係の別系統**。`SnapAngleDeg`（既定15度）は本刻みとは別の定数・別の丸め対象（角度） |
| **接続点（ポート）** | **影響なし**。`ClampPort`は整数境界へのみ丸める別機構（2節参照）。1/4化してもポートの置ける位置は変わらぬ |
| **メイン図面（ラダー本体）の自由線・接続点・画像挿入** | **無関係**。`Grep "Snap(" src/Ecad2.App/ViewModels/MainWindowViewModel.cs`で該当なし（"Snapshot"の部分一致のみ）——自由線等は連続値のmm実座標をそのまま扱い、そもそも本刻み機構を通らない別系統 |

**→ 分解能が効くのはパーツエディタの図形プリミティブ描画・ドラフト追従・移動ドラッグの差分計算のみ。他の観点（当たり判定・保存形式・描画・ポート・メイン図面）には及ばぬ。**

## 4. 「1セルを4×4」は縦横両方を指すか

**現状の実装は縦横対称**（`SnapCell`が`Snap(p.X)`・`Snap(p.Y)`に同じ既定値を用いる）ゆえ、殿の「4×4」という表現も素直に縦横均等と読める。**実装上どちらかの軸だけ異なる作りにはなっておらず、1/4へ変える場合も`Snap`の既定値を1箇所（`DefaultSnapFractionCells`）変えるだけで両軸に均等に効く見込み**である。

## 5-b. DoD6：原本GuiEcadの実装との突き合わせ

**原本ソースは当環境に在り**（`C:/Users/kojif/Desktop/生産物/gui_ecad/`）。台帳T-133裁定14の
「原本ソースが当環境に不在ゆえ突合できぬ」という記述は**縦向きモータの意匠についてのものであり、
ソース全体の不在を意味しない**——本調査で実際に`src/GuiEcad.App/`配下を`Grep`・`Read`し、
確かに存在することを確認した。

**原本の該当箇所**＝`src/GuiEcad.App/PartEditorWindow.xaml.cs:202-204`：

```csharp
private const double SnapStep = 1.0 / 16;                            // スナップ刻み（セル単位）
private static double Snap(double v) => Math.Round(v / SnapStep) * SnapStep;
private Vector2 SnapV(Vector2 v) => new((float)Snap(v.X), (float)Snap(v.Y));
```

**ecad2の実装（1節）と構造が完全に一致する**——(1) `SnapStep`/`DefaultSnapFractionCells`とも`1.0/16`
という同一の定数、(2) `Snap`は`double`ひとつを線形に丸めるスカラー関数、(3) `SnapV`/`SnapCell`は
X・Yへ独立に2回適用する（`Vector2`の2成分へ個別に`Snap`を呼ぶ形は、ecad2の`Point2D`の2成分へ
個別に`Snap`を呼ぶ形と同型）。**すなわち原本も「1辺を16等分（線形）＝1セルに256点」であり、
「1セルを16分割（面積・4×4）」ではなかった。**

**→ ecad2はこの点で原本を忠実に移植しており、変質・改悪は無い。** **殿の御記憶「確か16分割ぐらいで
設計したはず」は、当時の実装（`SnapStep=1/16`の線形刻み）とは異なっていたと見受けられる**——
**これは事実として申し上げるのみで、記憶と実装のどちらが「正しい設計意図」であったかを隠密が
判ずるものではない。** 御記憶には「確か」「ぐらい」という留保が最初から付されており、本調査は
その留保の妥当性を裏付ける形になった（実装は記憶より4倍細かかった、という一次ソースの事実）。

**結論としてDoD6に答える**：**原本も1辺16等分＝256点/セルであり、ecad2の実装と一致する。
「ecad2への移植で変質した」という筋ではなく、「原本設計時から一貫して1/16線形刻みであり、
殿の後年の御記憶（16分割＝4×4）とは異なっていた」という筋である。** 本件は仕様変更（狙った
分解能へ新たに変える）として扱うのが実情に即すと見受けるが、採否は殿の裁可を要する。
