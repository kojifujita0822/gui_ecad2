# 原本GuiEcad「その他図形」(3極記号)の縦向き描画・占有調査

隠密（key=1785485896132）記す。2026-07-31。家老采配より。**調査のみ・実装せぬ。**

前提＝`docs/ecad2-t133-guiecad-other-shapes-survey-onmitsu.md`（隠密既著）を読了済み。その他図形の中身（組込み記号10件・組込みパーツ2件等）は同書で確定済みゆえ本書では再掲せぬ。

## 結論（先に）

1. **縦向き3極記号は、アンカー行の上下各1セル・計2セル分（中心から±1セル）に描かれる**——原本コードに明記あり。
2. **原本には占有行の概念が無く、占有判定・当たり判定は`Pos.Row`との厳密一致のみ**。3極記号の上下に別要素を置くことを妨げぬ——**視覚的な重なりを構造的に許容している**。
3. **描画が及ぶ範囲（連続2セル、中心±1）と、占有行の境界（整数区切り）は噛み合わず、実際には3つの「行帯」（中心行・上下の隣接行）へ半端に触れる形になる**。これは「不具合」というより、**原本が占有行という概念自体を持たぬために生じた、設計の射程外の事象**である。
4. 3極記号はポート0個（自由配線）だが、**入線・出線は列境界の縦グリッド線ちょうどを通るよう意図的に設計されている**——殿の仰せの「配線が線上を通る」絵は、この入線・出線の設計に由来すると見受ける。
5. **【新材料】上記3の「3つの行帯に触れる」という実測は、殿裁定(C)「偶数はh+1行（高さ2なら3行）」と数として一致する**——(C)は、この3極記号の実際の描画実測に照らして妥当な数と見受けられる。

## 1. DoD1：縦向き3極記号の描画実体

`GuiEcad.Core/Rendering/SymbolGlyphs.cs:240-247`（コメント全文）：

```
// 1 単位 = k = width/2（CellWidth=2）＝1セル。
// 縦(V): 極は x=0/1/2（列境界＝縦グリッド線上）、流れは y∈[-1,1]（上→下）。
```

**`Breaker3P`（`:288-310`）・`ContactorMain3P`（`:313-328`）・`ThermalOverload3P`（`:331-`）はいずれも共通の`fMin=-1, fMax=1`（V時）を使い**、`Pole.P(f,g)`（`:256`）が`h=false`（V）のとき`Y=f*k`（`k=width/2=1`、3極記号は幅2固定）を返す。**すなわちY座標は`f∈[-1,+1]`の範囲、すなわちアンカー行の中心（`YRow(Pos.Row)`、Y=0相当）から上下各1セル、計2セル分に描かれる。**

**これはecad2側の理解（`ElementCatalog.DefaultCellHeight(Breaker3P)=2`、既存ドキュメントに「行中心から上下1セル」と明記）と完全に一致する。移植の際に描画の実体を正しく踏襲できていることが、原本との突合で裏付けられた。**

## 2. DoD2：占有行の概念が無い中での扱い——**厳密な単一行一致のみ**

原本の占有判定・当たり判定を直読した（`GuiEcad.App/MainPage.xaml.cs:663-683`）：

```csharp
private bool CellEmpty(int row, int col, ElementInstance? except)
{
    foreach (var e in _sheet.Elements)
    {
        if (e == except || e.Pos.Row != row) continue;   // ← 行の厳密一致のみ
        var (l, r) = PartResolver.BoundarySpan(e, _document.Library);
        if (col >= e.Pos.Column && col < r) return false;
    }
    return true;
}

private ElementInstance? HitTest(int row, int col)
{
    foreach (var e in _sheet.Elements)
    {
        if (e.Pos.Row != row) continue;                  // ← 同上
        ...
    }
    return null;
}
```

**`e.Pos.Row != row`という厳密な一致判定のみ**で、`CellHeight`という概念自体が存在せぬため（`Element.cs:44-56`に`CellWidth`のみ）、**要素の視覚的な高さは占有判定に一切関与しない**。

**→ 3極記号（視覚的に2セル分の高さ）を配置しても、その上下の行には別の要素を（列が空いてさえいれば）自由に置ける。原本はこれを妨げる仕組みを持たぬ。**

## 3. DoD3：描画範囲と占有範囲の食い違い——**在る。原本はこれを問題視していない**

**食い違いは明確に存在する**——描画は連続2セル（中心±1セル）だが、占有・当たり判定はアンカー行1行のみ。**上下の行に他要素を置けば、画面上は3極記号の絵とその要素が重なって見えるが、原本のロジック上は何の矛盾も検出されない。**

**原本がこれを不具合と見ていない根拠**：
- 原本は`docs/drawing-spec.md:38`（前回セッションで確認済み・本書で再確認せぬ既知の事実）に**「行をまたぐ配置は基本NG」という設計方針を明文化**しておきながら、**3極記号のような視覚的にまたがる記号については、占有判定に何の特別扱いも実装していない**。
- **これは「例外を意図して許した」というより、「占有行という概念自体を持たぬ原本の設計に、後から視覚的に大きい記号を追加した際、占有判定側の手当てが漏れた」という形に見える**（推測、事実と分けて記す）。**主回路3極記号がそもそもDRC・ネットリストの対象外（ポート0・自由配線）である以上、電気的な誤結線は起きようがなく、視覚的な重なりだけが残る実害の小さい漏れであったため、原本の開発時点で気づかれなかった、あるいは気づかれても後回しにされた**、と見受けられる。

**殿の御言葉（家老采配文引用）「原本にも3極部品を制御回路シートへ置けてしまうバグがあり未修正」と同種の性質——「原本自身が完全に整合の取れた設計ではない」という前例が、ここでも重なる形にござる。**

## 4. DoD4：接続点の位置——**ポート0個。ただし入線・出線は列境界の線上を通る**

3極記号はポートを持たぬ（既存調査書で確認済み、`ElementCatalog.cs:47-48`相当のコメント「主回路3極記号は自由配線（FreeLine）で結線するため接続点を持たない」）。

**ただし「入線」「出線」（各極の上下に伸びる線分、`Breaker3P`の`p.L(fMin,0,...)`・`p.L(...,fMax,0)`）は、列位置`c∈{0,1,2}`（V時、列境界＝縦グリッド線ちょうど）を通り、Y方向は`fMin=-1`から`fMax=1`まで、すなわちアンカー行の真上・真下の行の中心線あたりまで伸びる。**

**→ 殿の仰せ「接点が行の線の上に乗り、母線から伸びる配線もその線上を通っておる」という絵は、この入線・出線が列の境界線（縦グリッド線）に正確に一致するよう設計されている点に由来すると見受ける**（コメント`:242`「母線（自由直線）がグリッド線上で極に重なるようにする」と明記あり、まさに殿の御言葉どおりの設計意図）。

## 5. 新材料（開いた観点、家老の問いの外で気づいたもの）

### 5-1. 「3つの行帯に触れる」実測は、殿裁定(C)の数と一致する

3極記号(V)の描画はY∈[-1,+1]（連続2セル）だが、行が整数中心・半整数境界の格子（`YRow`）である以上、**この描画は「アンカー行（中心）を完全に覆い、上下の隣接行はそれぞれ半分だけ」触れる形になる**——連続量としては2セルだが、**触れる行の「本数」を数えれば3本（アンカー行・上・下）**である。

**殿裁定2026-07-31(C)＝「図面の占有行＝奇数はh行、偶数はh+1行（高さ2なら3行）」は、この実測（触れる行帯の本数＝3）と正確に一致する。** **偶数のときだけ+1する」という裁定の形は、恣意的な丸めではなく、実際にこの種の記号がどれだけの行帯に触れるかという実測に照らして妥当な数**と見受けられる（事実の裏付けとして報告するのみで、裁定の採否そのものは殿の領分）。

### 5-2. 自作パーツ側（PartEditorのFrameRect）とは異なる規約が併存している

自作パーツの`FrameRect`（H-2、`PartShapeGeometry.cs:98-109`）は**`2h-1`セルを完全に覆う**設計であり、境界がぴったり行の境目に一致する（P-148裁定の眼目そのもの）。**一方、組込みの3極記号は上記のとおり「連続2セル・行帯には半端に触れる」形**であり、**両者は「高さ」という同じ言葉の下で、実は異なる幾何的性質を持つ**——**自作パーツは占有行を過不足なく覆うよう設計されているのに対し、組込み3極記号は覆いきらず隣接行にはみ出す**。

**この非対称自体が、T-139の裁定(C)が組込み・自作の両方に同じ式（奇数h行・偶数h+1行）を当てはめてよいか、一考の材料になりうる**——自作パーツ（`PartDefinition.HeightCells`経由、将来Kind経路以外で高さを持つ場合）は「隙間なく覆う」性質を持つため、常に`2h-1`（奇数）が自然に成り立つのに対し、**組込み3極記号のような「連続2セル」の記号は、そもそも自作パーツの`HeightCells`とは異なる経路（`ElementCatalog.DefaultCellHeight`固定値2）で決まっており、裁定(C)の式が指す対象が実質「組込み3極記号1種類（h=2固定）」に限られる**——**将来h=2以外の組込み記号が増えた場合、その記号の描画実測もこの都度確かめる要がある**、と申し添える。
