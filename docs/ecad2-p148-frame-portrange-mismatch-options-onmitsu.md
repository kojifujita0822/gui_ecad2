## 1. 数式で確認した不一致（一次ソース）

`src/Ecad2.Core/Model/PartShapeGeometry.cs`——

```csharp
// 枠（FrameRect、増分1で中央基準化）
return (0.0, -h / 2, w, h);          // Y方向は ±h/2

// 接続点のクランプ（ClampPort）
int rowLimit = Math.Max(0, heightCells - 1);
int row = Math.Clamp(..., -rowLimit, rowLimit);   // ±(h-1)
```

| h | 枠の範囲（±h/2） | 接続点の範囲（±(h-1)） | 一致するか |
|---|---|---|---|
| 1 | ±0.5 | ±0 | 一致（接続点は枠の内側） |
| 2 | ±1.0 | ±1 | **一致（h=2のみの偶然）** |
| 3 | ±1.5 | ±2 | **不一致——接続点が枠の外まで動ける** |
| 4 | ±2.0 | ±3 | 不一致（差はさらに開く） |

**再現手段**＝`h/2`と`h-1`をh=1〜4で計算するだけ（`grep -n "rowLimit\|FrameRect" src/Ecad2.Core/Model/PartShapeGeometry.cs`で式を確認）。

## 2.【DoD3】原本ではどうか——**GuiEcad原本にも同一の不一致が存在する**

`C:\Users\kojif\Desktop\生産物\gui_ecad\src\GuiEcad.App\PartEditorWindow.xaml.cs`を直読した。

**枠の描画**（本日采配6で確認済み、再掲）——
```csharp
private double Sy(double cy) => _originY + (cy + _h / 2.0) * _cellPx;
// 枠はSy(-_h/2.0)を上端としてY方向±h/2を占める
```


**併せて確認**＝GuiEcad側の高さ入力（`HeightBox`）は`Math.Clamp(..., 1, 12)`（`:189`）で**h=12まで許容**——原本でもh≥3の不一致は理論上到達可能な設定範囲にある（**GuiEcad側で実際にh≥3のパーツが作られた形跡があるかは本調査では未確認**）。

## 3.【DoD2】既存自作パーツへの影響

### 3-1. 組込み15件（`BasicPartTemplates.cs`）——**全て高さ1、無影響**

`grep -c "HeightCells"`で15件全てが`HeightCells = 1`であることを機械確認済み（本日、`docs/ecad2-t133-guiecad-motor-and-builtin-parts-survey-onmitsu.md`でも既出）。h=1では枠も接続点範囲も±0で一致するため、**いずれの案でも挙動は変わらぬ**。

### 3-2. 実ファイル18件——**忍者の「全て高さ1」は一部訂正を要する**

実際に`マイドキュメント\Ecad2\図形\`配下の`.gcadpart`ファイル全件（18件、直読・機械確認）を洗った——

| ファイル | heightCells | 備考 |
|---|---|---|
| 標準15件（a接点・b接点・コイル等） | **1** | 組込みと同一、無影響 |
| `自作\T133PDFOVER.gcadpart` | 1 | 別調査（T-060/T-080系）の検体、無影響 |
| `自作\T133INC1H2.gcadpart` | **2** | **T-133増分1検証時の検体（忍者作成と見受ける）**。h=2ゆえ枠・接続点範囲は一致（境界事例） |
| `自作\T133INC1H3.gcadpart` | **3** | **同上、h=3。ports P1(rowOffset=-2)・P3(rowOffset=+2)が実際に保存済み**——**枠の範囲±1.5の外に既に接続点がある状態そのもの** |

**訂正**＝「既存は全て高さ1」は**組込み15件＋大半の実ファイルには正しいが、`自作`フォルダに残る検証用検体2件（T133INC1H2・T133INC1H3）は該当しない**。特にT133INC1H3は**本件の不一致を体現した実例そのもの**（忍者が増分1の検証時に作成したと見受ける、日付・命名からの推測）。

**ただしこの2件は実運用データではなく検証用の残置検体と見受ける**（`T133PDFOVER`が引き継ぎ書で「対照撮影用の残置」と記録されているのと同型）。**実際のユーザーデータへの影響という観点では、忍者の「全て高さ1ゆえ影響なし」は実質的に成立する**——**ただし文字どおり「18件」を指すなら不正確であった**。

### 3-3. 各案が採る場合の実データへの影響（事実）

- **案(a)（`rowLimit`を`±h/2`へ揃える）**——**次にT133INC1H3を開いた際、`rowOffset=±2`のポートが読込/保存経路で再クランプされ`±1`または`±1.5`丸めの整数へ変わりうる**（クランプの実装次第で挙動が変わる、**設計判断を要する**）。**既存データの値が黙って変わる**という性質を持つ
- **案(b)（枠を`±(h-1)`へ広げる）**——**T133INC1H3の`rowOffset=±2`はそのまま**（既に範囲内）。**視覚的な枠が広がるだけで、保存済みのポート値は一切変わらぬ**
- **案(c)（現状維持）**——変化なし

## 4.【DoD1】選択肢の整理——事実の列挙（3択＋補足1）

家老の粗い見立て(a)(b)(c)に加え、**一次ソースを読む過程で見えた事実を1つ補足する**——

### 補足：増分3（占有・ヒットテスト）は既に`±(h-1)`を採用しており、`ClampPort`と「基準が揃う」と明記済み

`MainWindowViewModel.cs:2781-2792`（`IsWithinGridBounds`のdocコメント、殿裁定11=H-2）——

> 高さHの要素は`pos.Row`を中心として上下へ`H-1`行ずつ...**接続点の`ClampPort`が用いる
> `rowLimit = heightCells - 1`と同じ式であり、両者の基準が揃う。**

**これは事実として重要**——**メイン図面上の要素占有範囲（増分3、殿裁定11）と、パーツエディタの接続点可動範囲（`ClampPort`）は、既に同じ`±(h-1)`という式で意図的に揃えられている**。**揃っていないのはパーツエディタの「枠」（視覚表示）だけ**、という構図になる。

この事実を踏まえると——

- **案(a)（`rowLimit`を`±h/2`へ狭める）を採ると、`ClampPort`と増分3の占有範囲の間に「揃う」関係が新たに崩れる**（今度はメイン図面側との不一致が生まれる）
- **案(b)（枠を`±(h-1)`へ広げる）を採ると、枠・接続点・メイン図面占有範囲の3者が揃う**

**これは事実の指摘であり、隠密の推奨ではない**——3者の関係がどうなるかを示したのみ。

### 隠密の推奨（事実と分けて記す）

**あくまで隠密の見立てとして**、上記の「3者が揃う／崩れる」という事実に照らせば**案(b)が構造的に一貫する**方向と映る。ただし**視覚的な枠が大きくなることの見た目・使用感（パーツエディタの操作感）への影響はUI/UX判断であり、殿の判断事項**と考える。
