## 2. 未測だった一経路 → **導線を特定した**

**旧記録の4-1節**＝「右クリックメニューが『削除／機器名変更/コメント編集』の三つのみで、行削除の
導線に辿り着けなんだ」。**理由が判明**——右クリックした位置が**要素そのもの（またはコネクタ）の上**
だったため、`MainWindow.xaml.cs`の右クリックハンドラが要素分岐（削除／機器名変更/コメント編集の
3項目）へ入り、行操作メニューの`else`分岐（`:2161-2185`）へ到達しておらなんだ。

**行操作メニュー（「行Nを削除」＝`DeleteRowAtCommand`）が出るのは、要素・縦コネクタ・グループ枠・
画像のいずれにもヒットせぬ「空セル」を右クリックした場合のみ**（`MainWindow.xaml.cs:2161`の`else`）。

### 2-1. コードから読み取れる、旧記録が測っておらぬ経路の重み

`DeleteRowAtCommand`の実装（`MainWindowViewModel.cs:3785-3809`）——

```
var removed = RowOps.DeleteRow(sheet, row);   // 対象行の要素をまとめて削除
...
if (SelectedCell is GridPos sc && sc.Row > row)
    SelectedCell = sc with { Row = sc.Row - 1 };   // ← 削除行が選択行より上のときだけ動く
NotifySelectedElementChanged();                     // ← 常に呼ぶ(無条件)
```

**削除対象行が選択中セルの行と同じか、それより下（`sc.Row <= row`）のとき、`SelectedCell`自体は
書き換わらず setter は走らぬ**——**この場合に限り、症状の有無は`NotifySelectedElementChanged()`の
明示呼び出し一本のみに懸かる**。これがコード内コメント（`:3798-3800`）で名指しされている
「削除対象行そのものを選択中でも無条件で呼ぶ」の対象そのものにござる。

**すなわち、正しく的を絞るには「選択中の要素と同じ行、またはそれより下の行を削除する」操作が要る**
——**選択行より上を消すだけでは、`SelectedCell`のsetter経由の通知と混ざり、明示呼び出し単体の効果を
切り分けられぬ**。

### 2-2. 手順（案）

1. 要素を1つ配置し、選択してプロパティパネルを表示させる（行 R、列 C₁とする）
2. **同じ行 R の、要素の無い別セル（列 C₂）を右クリック**——要素上を右クリックすると3項目メニューに
   なってしまうため、必ず空セルを狙う（**行に他の要素が無い列を選ぶ**）
3. 「行{R+1}を削除」をクリック（`sc.Row == row`となり、`SelectedCell`のsetterは走らぬ経路）
4. 削除直後、プロパティパネル・プレースホルダの状態を観測（旧記録と同じくUIA二軸＋スクショ）

**予備確認**——**行削除は「行全体の消去」ゆえ、対象行に選択要素以外の要素が同居する場合は巻き添えに
なる。** 検体は**対象行に要素を1つだけ置いた最小構成**で臨む（余計な変数を持ち込まぬ）。

### 2-3. 既存五経路との関係

旧記録の経路1〜3（編集メニュー削除・`Delete`キー・右クリック削除）は、いずれも**`DeleteSelectedElement`
系**（`SelectedCell`のsetter経由）を通ると見立てられる。**本経路（行削除）はそれとは別の呼び出し元
（`DeleteRowAtCommand`）ゆえ、五経路のいずれとも重複せぬ第六の経路**にござる。
