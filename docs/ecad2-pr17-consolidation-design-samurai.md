## 5-2. 【追記 2026-08-06】`ReplaceDocument` 経路に**実害は生じぬ**——間接的に塞がっておった

**家老の采配「静的に詰められる範囲があれば進めよ」に応じ、§6-1に区切った未測定を解いた。**
**結論＝忍者の発見は「明示的な通知が無い」という構造の事実としては正しいが、
実害（右下パネルが空白のまま残る）は生じぬ。**

### 【肝】`HasNoPropertySelection` の消費先は**ただ一箇所**

`src` 全体で5箇所しか現れぬ（侍が機械的に洗った）——定義1・通知3・**消費1**。

**消費＝`MainWindow.xaml:1574`**、TextBlock「要素を選択してください」の `Visibility` のみ。
**すなわち症状の形は「案内文が出ぬまま右下が空白になる」の一つに限られる**
——`P-169` の実機所見（削除後、右下が完全な空白）と同一の形にござる。

### 【救い】`ReplaceDocument` は通知する setter を**必ず2つ通る**

| 行 | 代入 | setter が `HasNoPropertySelection` を通知するか |
|---|---|---|
| `:3573` | `_selectedCell = null` | **通知せぬ**（setter をバイパスする直接代入） |
| `:3588` | `SelectedImage = null` | **通知する**（`:1298`） |
| `:3592` | `SelectedFrame = null` | **通知する**（`:1488`） |

**両 setter とも `SetProperty` の戻り値を見ておらぬ**（`:1296-1298`／`:1486-1488`）
——**同値（null → null）でも通知が飛ぶ無条件の形**にござる。
**ゆえに `ReplaceDocument` は必ず2回の通知を出し、最後の `:3592` の時点では
`_selectedCell`・`SelectedImage`・`SelectedFrame` の三つとも null＝正しい値（true）が伝わる。**

### 【対照】`DeleteSelectedElement` が救われぬ理由

**削除経路は `SelectedImage`／`SelectedFrame` の setter を一度も通らぬ**（`:2521-2557` を全文確認）。
**`ForceCancelDragElementIfAny()` は呼ぶが、これは通知経路が別にござる。**
**——`P-169` が実機で確定しておるのと、本経路が救われておるのとは、この一点で分かれる。**

### 【されど段2の値打ちは変わらぬ】救いが**暗黙**であるゆえ

**現状の `ReplaceDocument` は「他のプロパティの setter が無条件通知である」ことに依存して塞がっておる。**
**この依存はコードのどこにも書かれておらぬ。**
**もし将来 `SelectedImage` setter が `if (SetProperty(...))` でガードする形へ『整理』されれば、
救いは黙って消える**——そして `ReplaceDocument` 側には明示の通知が無いゆえ、誰も気づかぬ。

**段2で基準へ足せば、この暗黙の依存が明示に変わる。**
**すなわち段2の狙いは、本経路については「穴を塞ぐ」ではなく「偶然の救いを設計に変える」ことにござる。**

### 【射程を区切る】

- **一次ソースで確定した事実**＝(a) 消費先が1箇所であること (b) 両 setter が無条件通知であること
  (c) `ReplaceDocument` が両 setter を必ず通ること
- **推論**＝ゆえに WPF のバインドが再評価され、最後の通知で正しい値になる
- **測っておらぬ**＝**実機での見え方**。**これは忍者の領分ゆえ踏み込まぬ**（家老の申し付け）
