## 3. 【問い2】機械的検出は成り立つか——**成り立つ。ただし条件が二つある**

**家老の案（`SelectedElementXxx`を機械的に列挙し、通知箇所を数える）を実際に走らせて検算した。**
**そのままでは二つの穴がござる。**

### 3-1. 穴(a)＝**「件数=4」を条件にすると偽陽性が2件出る**

**再現手段**＝`Select-String "OnPropertyChanged\(nameof\(<名>\)\)"` で件数を数える。

| プロパティ | 件数 | 内訳 |
|---|---|---|
| `SelectedElementKindDisplay` | **5** | 共通4箇所 ＋ **固有1**（`:2242`） |
| `SelectedElementSetpointSliderValue` | **5** | 共通4箇所 ＋ **固有1**（`:2423`） |
| 他11件 | 4 | 共通4箇所のみ |

**この2件は共通4箇所にすべて載ったうえで、自分だけの追加通知を持つ。**
**数だけを見れば「4でない」と鳴るが、漏れではござらぬ。**

### 3-2. 穴(b)＝**命名規約で列挙すると4件が網から外れる**

**`(Is)?SelectedElement\w+` で拾えるのは13件。同じ通知ブロックに居ながら拾えぬものが4件ござる**——
**`SelectedCellDisplay`／`SelectedElement`／`HasSelectedElement`／`HasNoPropertySelection`。**

**新設プロパティが規約外の名を持てば（例＝`HasXxx`形式）、検出網に入り申さぬ。**
**これは`onmitsu.md`「探索条件を書いたら『対象の種類は足りておるか』を問う」の型にござる**
——**`.cs`だけ見て`.xaml`を落とした先例と同根。**

### 3-3. **両方を避ける形＝「塊どうしの差集合を取る」**

**命名にも件数にも依存せぬ。**手順は三つ——

1. `OnPropertyChanged(nameof(X));` の行を全て拾い、**行番号が連続する塊**へまとめる
2. **4件以上の塊**を「一括通知ブロック」と見なす
3. **塊どうしを突き合わせ、一部の塊にしか居ないものを出す**

**実際に走らせた結果**——4件以上の塊は**7つ**。うち**行496・2540・2677・3630の4つ**が
「選択切替の一群」をなし、**その4つすべてに載るものが15件**、**非対称が2件**であった。

**この形なら、本日の漏れは機械的に出申す**——**「他の塊には居るが、この塊には居ない」として現れるゆえ。**

> **【重大な訂正・2026-08-05、某が家老の第三案を検分する過程で己の誤りに気づいた】**
> **初稿は上に続けて「T-107の漏れも出申す」と書いておったが、それは誤りにござる。**
> **T-107は`SelectedElementComment`が4箇所すべてに無かった**（本書2節の表に某自身がそう記しておる）。
> **4箇所すべてに無ければ「他の塊には居る」が成り立たず、差集合には一切現れ申さぬ。**
> **すなわち差集合の検出は、本日型（一部漏れ）は捕らえるが、T-107型（全箇所漏れ）を構造的に取り逃す。**
>
> **【機序】某は本書2節で「落ちた箇所＝T-107は4箇所すべて／本日は4箇所中1箇所」と表に書き分けておきながら、
> 3節でその区別を勘定に入れなんだ。** **`onmitsu.md`「『別系統がある』と己で指摘したなら、
> その後の全ての数え上げでその別系統を数えたか毎回確かめよ【MUST】」——**
> **己の指摘を、己が忘れる**——**その条が説く型そのものにござる。**
> **表と文を書き分けながら文が表を裏切った点では「表と文の両方を書いたら、
> 文の主張を表の行で1つずつ指させよ【MUST】」の型でもある。二条が同時に効く場面であった。**

**【射程・某が自ら区切る】塊の同定は「行番号が連続すること」に頼っており申す。**
**間に空行やコメントを挟む書き方をすれば塊が割れ、検出が崩れ申す。**
**現状のコードは4ブロックとも連続しておるゆえ成り立つが、これは実装の作法に依存した前提にござる。**
**制度化するならば、この前提そのものを`samurai.md`へ「一括通知ブロックに空行・コメントを挟まぬ」と
書き添えるのが筋と考え申す**（**そこまで縛るべきかは家老・侍の判断**）。

## 4. 【所見】網の形について——`PropertyChangedForTest`は**塞ぐ範囲が違う**

**家老の見立て3（侍が本日新設したテストの形を網に使う）について、一点申し添える。**

**テストは「そのプロパティが通知されること」を1件ずつ固定する形にござる。**
**すなわち——新設プロパティごとに、書く者がテストを1本書かねばならぬ。**
**書き忘れれば網は無い。** **機序2（取りこぼし）には効くが、機序1（失念）には効き申さぬ**
——**失念する者は、テストも書き忘れるゆえ。**

**対して差集合の検出は、書く者が何もせずとも全件を横断し申す。**

**→ 両者は代替ではなく補完にござる。**
- **差集合の検出**＝**漏れを見つける**（全件横断・書き手の作業不要）
- **`PropertyChangedForTest`のテスト**＝**直した後に再発を止める**（1件ずつ・書き手の作業要）

**制度として一つだけ採るなら、某は前者を推し申す**——**後者は「書く」という作業が要り、
その作業自体が本件の失敗要因（書き忘れ・取りこぼし）と同じ性質を持つゆえ。**

## 5. 【副産物・範囲外の気づき】試作を走らせたら、非対称が2件出た。うち1件は穴の疑いが濃い

**家老の問い2に答えるため差集合を実際に走らせたところ、
「4ブロックすべてには載っておらぬもの」が2件出申した。**

### 5-1. `SelectedCellDisplay`（4ブロック中2箇所）＝**意図。穴ではない**

**在るのは`SelectedCell` setter（`:496`）と`ReplaceDocument`（`:3630`）のみ。**
定義＝`public string SelectedCellDisplay => SelectedCell is { } pos ? $"行{pos.Row + 1}/列{pos.Column}" : "未選択";`

**`SelectedCell`のみに依存する**ゆえ、**`DeleteSelectedElement`・`NotifySelectedElementChanged`では
`SelectedCell`が変わらぬ＝通知不要**にござる。**筋が通っており申す。**

### 5-2. `HasNoPropertySelection`（4ブロック中**1箇所**）＝**穴の疑いが濃い**

**在るのは`SelectedCell` setter（`:496`）のみ。**
定義（`:1311`／検索文字列＝`public bool HasNoPropertySelection`）＝

```csharp
public bool HasNoPropertySelection => !HasSelectedElement && !HasSelectedImage && !HasSelectedFrame;
```

**`HasSelectedElement`に依存しており、その`HasSelectedElement`は4ブロックすべてで通知されておる。**
**にもかかわらず`HasNoPropertySelection`は1箇所のみ。**

**とりわけ`DeleteSelectedElement()`（`:2521-2557`）を丸ごと直読して確かめた**——
- `sheet.Elements.Remove(el)` するのみで**`SelectedCell`を書き換えておらぬ**
- **コード内コメント`:2534`が「`DeleteSelectedElement`は`SelectedCell`のsetterを経由しない」と明記**（一次ソースの裏づけ）
- `HasSelectedElement`は`:2541`で通知されるが、**`HasNoPropertySelection`は通知されぬ**

**→ 要素を削除すると`HasSelectedElement`が真→偽、ゆえに`HasNoPropertySelection`は偽→真へ変わるはずだが、
通知が飛ばぬ。** **右パネルの「要素を選択してください」プレースホルダが出ぬままになる恐れがござる。**

**【時制＝既に起きておる】** 将来の条件待ちではなく、**現行コードの構造として成立しており申す。**

**【射程・某が自ら区切る】静的読解のみにござる。**
**実際に画面でプレースホルダが出ぬところまでは見ておらぬ。**
**WPFのバインディングが別経路（親コンテナの再評価等）で更新される可能性は、静的には否定しきれ申さぬ。**
**実機での確認が要る。**

**【この一件が、問い2への最良の答えになり申した】**
**「機械的検出は成り立つか」を確かめるために試作を走らせたところ、
その試作が、誰も見ておらぬ穴を1件掘り当てた。**
**T-107（1件目）・本日の要修正1（2件目）に続く3件目の候補にござる**——
**しかも本日の増分5とは無関係な、既存コードに現存するもの。**

# 7. 【家老の第三案への検分】単体テストとして一度だけ常設する

**家老の案**＝差集合の検出を、手順ではなく**単体テストとして一度だけ常設**する。
書く作業は初回のみゆえ、某の懸念（書く作業が失敗要因と同じ性質）は当たらぬのではないか、というもの。

## 7-1. 【結論】**方向は正しい。されど比較軸を替えねばならぬ**

**「一度書けば以後は自動で鳴る」という家老の見立ては正しく、某の懸念は確かに解け申す。**
**問題は案の中身ではなく、某が渡した比較軸（差集合）の方にござった**——**上記の訂正のとおり、
差集合ではT-107型（全箇所漏れ）を取り逃す。**
**その軸のままテストへ常設すれば、「網を張った」という安心だけが残り申す。**

## 7-2. 【対案】比較軸を**「値が変わったか」対「通知が飛んだか」**へ替える

**依存関係は静的には取れぬが、実測はできる**——単体テストならばこそ。

1. 要素Aを選択し、**VMの全publicプロパティの値を記録する**（リフレクション）
2. 経路を1つ走らせる（`SelectedCell`変更／`DeleteSelectedElement`／配置／文書差し替え）
3. **全publicプロパティの値を再記録し、変わったものを出す**
4. **同じ経路で発火した`PropertyChanged`の名前を集める**（`PropertyChangedForTest`が使える）
5. **「値が変わったのに通知が飛ばなかったもの」を出す**——**これが穴にござる**

**この軸なら両型とも捕らえ申す**——

| | 差集合（某の初案） | 値対通知（対案） |
|---|---|---|
| 本日型（4箇所中1箇所漏れ） | **鳴る** | **鳴る** |
| **T-107型（4箇所すべて漏れ）** | **鳴らぬ** | **鳴る**（値は変わるが通知が無いゆえ） |
| `HasNoPropertySelection`（5-2） | 鳴る | **鳴る** |
| 命名規約への依存 | 無し | 無し |
| 新設時に人が書く作業 | 無し | 無し |

**しかも「4経路が同じ集合を飛ばすべき」という前提そのものが不要になり申す**——
**意図的な非対称（`SelectedCellDisplay`＝`SelectedCell`のみに依存）も、
その経路では値が変わらぬゆえ自然に除かれる。例外リストが要らぬ。**

## 7-3. 技術的に成り立つか——**4経路とも public API から到達できる**

| 経路 | 到達手段 | 確認 |
|---|---|---|
| `SelectedCell` setter | `vm.SelectedCell = ...` | **侍が本日書いたテストBで実証済み** |
| `DeleteSelectedElement` | public メソッド（`:2521`） | ○ |
| `NotifySelectedElementChanged` | private だが `PlaceElementAtSelectedCell`（public）が呼ぶ（`:3202`／`:3283`） | ○ |
| `ReplaceDocument` | private だが `NewDocument()` 等が呼ぶ。**侍のテストが既に`vm.NewDocument()`を使うておる** | ○ |

**`PropertyChangedForTest`（`ViewModelBase`）が発火名を拾う器として既に在る**（本書4節）。
**新たな基盤は要り申さぬ。**

## 7-4. 【射程・某が自ら区切る】この対案にも限界が三つござる

1. **要素Aと要素Bが似すぎておれば値が変わらず、その項目は検められ申さぬ**
   ——**種別・デバイス名・各パラメータを十分に違えた2要素を用意する要がある。**
   **`onmitsu.md`「テスト入力の対称性・退化性チェック（PR-27）」がそのまま効く場面にござる。**
2. **getterが副作用や例外を持つプロパティは、全件走査で問題を起こしうる**——除外リストが要る見込み。
   **その除外リストが肥れば網は緩み申す**（差集合案の例外リストと同じ弱点が、規模は小さいながら残る）。
3. **某はこの対案を実装しておらぬ。上は静的な設計の見立てにござる。**
   **実際に書けば、リフレクションでの全件走査が思わぬ副作用を呼ぶ等の障りが出るやもしれ申さぬ。**
   **成否は侍が一度書いてみるまで確定いたし申さぬ。**

## 7-5. 【家老の自問への答え】処方を足されたのは癖ではなく、要る場面にござった

**家老は「これは家老が処方を足したもの＝貴殿が指摘した癖にござる」と自ら区切られた。**
**されど本件は、足されて然るべき場面であったと某は見申す。**

**理由**——**某の初案（差集合）には某自身が気づかなんだ穴があり、
それが露見したのは、家老が「テストとして常設できぬか」と別の形を提示なされたゆえにござる。**
**某は形を問われて初めて、その形で本当に両型が鳴るかを検め、己の誤りを見つけ申した。**

**すなわち処方を足すことが、観測の検算になり申した。**
**「観測は隠密、処方は家老」という区分は役儀の話であって、
処方を出してはならぬという意味ではござらぬ**——**本日はその逆が働いた一件にて、
本書1節の表に添えて記し置く。**

# 8. 【侍の上申の検証】インライン複製を`NotifySelectedElementChanged()`へ統合できるか

**侍の上申**＝3箇所（`SelectedCell` setter・`DeleteSelectedElement`・`ReplaceDocument`）は
既存の`NotifySelectedElementChanged()`を呼ばず各々インライン複製を持つ。
**統合すれば「4箇所に分けて書く」こと自体が構造上できなくなる**、というもの。

## 8-1. 【結論】**成り立ち申す。ただし単純置換では通知が2件消える**

**4箇所の中身を1件ずつ突き合わせた結果**（**再現手段**＝`OnPropertyChanged(nameof(X));`の行を拾い、
行番号が連続する塊へまとめて内容を比較）——

| 箇所 | 件数 | 内訳 |
|---|---|---|
| **`NotifySelectedElementChanged()`**（`:2675-2692`） | **15** | 基準となる15件（`SelectedElement`〜`SelectedElementComment`） |
| **`DeleteSelectedElement`**（`:2540-2554`） | **15** | **基準と完全同一** |
| **`ReplaceDocument`**（`:3630-3645`） | **16** | `SelectedCellDisplay`（`:3630`）＋ 基準15件 |
| **`SelectedCell` setter**（`:496-512`） | **17** | `SelectedCellDisplay`（`:496`）＋ 基準15件 ＋ `HasNoPropertySelection`（`:512`） |

**15 + 1 = 16／15 + 2 = 17**——**数が合い申す。**

**すなわち3箇所とも、基準15件を丸ごと含んだうえで、前後に0〜2件を足した形にござる。**
**侍の見立て「インライン複製」は正確にて、統合は成り立ち申す。**

## 8-2. 【家老の問い3】消える通知・増える通知——**置換の形次第にござる**

**単純置換（`NotifySelectedElementChanged();`のみに置き換える）なら2件消え申す**——
- `SelectedCellDisplay`（`SelectedCell` setter・`ReplaceDocument`の両方から）
- `HasNoPropertySelection`（`SelectedCell` setterから）

**前後に残す形なら、消えも増えもいたし申さぬ。** 具体には——

```csharp
// SelectedCell setter（if (SetProperty(...)) の内側）
OnPropertyChanged(nameof(SelectedCellDisplay));
NotifySelectedElementChanged();
OnPropertyChanged(nameof(HasNoPropertySelection));

// ReplaceDocument
OnPropertyChanged(nameof(SelectedCellDisplay));
NotifySelectedElementChanged();

// DeleteSelectedElement
NotifySelectedElementChanged();   // 前後とも不要（完全同一ゆえ）
```

**通知の内容も順序も完全に保たれ申す**（基準15件は4箇所とも同じ並び順であることを確認済み）。

**【`SetProperty`早期returnの内か外か】＝内にござる。**
`SelectedCell` setterの通知ブロックは`if (SetProperty(ref _selectedCell, value))`の**中**にあり、
**値が変わった時のみ走る。** **統合後もif内で呼ぶ形になり、挙動は変わり申さぬ。**

## 8-3. 【家老の問い2】`ReplaceDocument`の無縁な通知——**塊の外ゆえ取りこぼしは出申さぬ**

## 8-4. 【`P-169`との関係】**統合そのものでは消え申さぬ。消す機会を作るのみ**

**家老の見立て「統合が入れば`P-169`も同時に消える筋やもしれぬ」——条件付きで正しゅうござる。**

**`HasNoPropertySelection`は`SelectedCell` setterにしか無い。**
**統合しても、それが他3箇所へ広がることはござらぬ**——**むしろ単純置換なら setter からも消え、
`P-169`は悪化いたし申す。**

**消すには`NotifySelectedElementChanged()`の中へ`HasNoPropertySelection`を足す要がござる。**
**そうすれば4箇所すべてで通知され、`P-169`は構造的に消え申す。**

**すなわち——統合は`P-169`を消すのではなく、「1箇所直せば4箇所に効く」形を作り申す。**
**そここそが統合の値打ちにて、家老の見立ての筋は通っており申す。ただし一手足りませぬ。**

**なお`SelectedCellDisplay`を中へ入れるか否かは別の判断にござる。**
`DeleteSelectedElement`では`SelectedCell`が変わらぬゆえ通知は不要なれど、**入れても害は無い**
（値が変わらぬプロパティへの通知は、束縛が再評価されるだけ）。
**単純にするか、意図的な非対称を残すか——某は判断を持ち申さぬ。侍・家老の領分にござる。**
