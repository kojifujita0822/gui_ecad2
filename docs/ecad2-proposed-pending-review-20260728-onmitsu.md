### 【留意】P-123・P-124 は「ユーザー実害なし・**検証実害あり**」という特殊な位置にある

両件とも原記述は「**視覚的には正しく表示され、影響なし**」＝**ユーザーへの実害は無い**。
**この判定自体は今も正しい。**

**だが本日、我らの検証作業における実害が顕在化した**——忍者のT-133実機調査で
**「AvalonDockのツールバータブは`TabItem.Name`で判別できぬ（型名になる）。子の`ControlType.Text`で
同定する要がある」**と判明し、**`ecad2-ui-automation`スキル6.1節へ制度化された**
（引き継ぎ書§4）。**P-123 がまさにその箇所にござる。**

**すなわち「実害なし」の前提は、ユーザー視点では保たれ、検証者視点では崩れた。**
**ecad2 はUIオートメーションで実機検証する体制ゆえ、UIA Name の型名フォールバックは
「見た目に出ぬが我らの手間を増やす」という位置を占める。**

**それでも据え置きが妥当と判ずる**——**迂回策（子`Text`要素で同定）が確立し、スキルへ落ちて
おるゆえ、既に実務上は塞がれておる**。**修正すれば迂回が不要になるという利得はあるが、
急ぐ理由には至らぬ。**

## 派生提案・気づき（落とし先つき）

1. **【最重要】pendingの棚卸しは「時間軸」だけでなく「収束先」でも束ねられる** —
   前回の収穫は「過去のタスク完了で前提が変わったもの」という**時間軸**の切り口であった。
   今回は**5件が一つの未着手タスク（β-2/β-3）へ収束する**という**別の切り口**が出た。
   **前者は『いつ拾えるようになったか』を見る／後者は『どこで一度に拾えるか』を見る。**
   **着手前のタスクへ観点として束ねる方が、個別に拾うより安い。**
   → **落とし先＝`onmitsu.md`「`proposed.md`のpending項目棚卸しの観点」節へ一項追加**
   （現行の節は「ラベルだけで判じるな」「前提条件の成立を見よ」の2点＝**いずれも時間軸の観点**
   のみゆえ、**収束先の観点が抜けておる**）
2. **「次の機会に併せて」と申し送った項目は、その機会の消滅を誰も見ておらぬ** —
   P-131 は「T-127実機確認の折に」と段取りされたが、**T-127がDoneになった時点で機会は消えた**。
   **申し送りに機会を紐づけると、その機会が閉じた折に宙に浮く。**
   → **落とし先＝`karo.md` 非同期委譲の作法**（「**次の機会に併せて**」と書く時は、
   **その機会が閉じた場合の扱いも併記する**。**数を書く時に手段を併記する10項と同じ形**にござる）。
   **家老の判断を仰ぐ**
3. **UIA Name の型名フォールバックは「ユーザー実害なし・検証実害あり」という第三の位置を持つ** —
   P-123・P-124 の「実害なし」判定は**ユーザー視点では今も正しいが、検証者視点では本日崩れた**。
   **UIオートメーションで検証する体制を採る以上、この軸は独立して評価する価値がある。**
   → **落とし先＝`ecad2-ui-automation`スキル**（6.1節に迂回策は既載ゆえ、**「なぜそうなるか＝
   P-123/P-124 という既知の起票がある」への相互参照**を足す程度で足りる）。**家老の判断を仰ぐ**
