## 1. 対象仕様

### 1.1 背景（要約、詳細は出典参照）

`PartOptimizer.ClampPortsToFrame`（T-068増分3-c新設）は接続点を基準枠の範囲内へ正規化するが、
重複チェックを持たない。「BoundaryOffset同一・RowOffset違い」の接続点2個を持つ部品の基準枠を
縮めて保存すると、両方が完全同一座標へ収束しうる（P-129、忍者実機再現・隠密原本比較調査済み）。
`NetlistBuilder.BuildElementConnections`が厳密不等号比較で最左・最右ポートを決めるため、この
収束は「本来分離されるべき左右ネットが同一ネットへ統合される誤結線」という実害を持つ。

### 1.2 殿裁可の対処方針＝二本立て（検証A＋検証B）

起草後、侍より「完全同一座標の拒否（定義1）だけでは実害が残る」との上申あり。隠密が
`NetlistBuilder.BuildElementConnections`を一次ソースで検算し、侍の主張の技術的正しさを確認
（1.2b節に経緯を残す）。さらに侍が`NetlistBuilder.Build`を実走させ、「一部のポートだけが同じ
`BoundaryOffset`を持つ」ケース（3ポート中2つが同一境界）では**実害が生じない**ことを実測で
発見——**隠密の構造からの証明（実運用パーツは`heightCells=1`ゆえ原理的に該当構造なし）と
侍の実測（実際に`NetlistBuilder`を回して確かめる）が別経路から同じ結論に収束し、かつ実測が
隠密の当初設計の見落とし（境界条件）を補正するWチェックが成立した**。

**殿裁可＝以下2つの独立した検証を両方とも保存時に行う**：

- **検証A（重複）＝完全同一座標の対を拒否**。RowOffset・BoundaryOffset とも一致するポートの
  対が存在すれば拒否。データ一意性の軸（隠密の当初設計＝旧「定義1」そのもの）。
- **検証B（縮退）＝全ポートの`BoundaryOffset`が同一なら拒否**。「2点が一致」ではなく
  **全ポート**が対象——`NetlistBuilder`の`pl`/`pr`決定（最小・最大の`BoundaryOffset`を持つ
  ポート）が実際に縮退する（`pl == pr`になる）条件そのもの。実害を断つ軸。**ポート2個以上に
  限る**（家老裁定1、1.3節参照）。

**家老裁定2件**：
1. 検証Bは「ポート2個以上」に限る——ポート1個は既存「2点未満」検査で`NonSimulated`のみ通過し、
   `NonSimulated`は`CreatesComponent=false`ゆえ縮退の実害が生じない（二重の壁）。
2. `NonSimulated`は検証A・Bいずれからも除外しない——隠密の所見「ポート数下限の除外と座標重複の
   除外は別軸」を採用（4.6節参照）。

### 1.2b 経緯（旧「重複の定義分岐」の顛末、記録として残す）

当初「重複の定義」が2通り立つとされた——定義1（完全同一座標）／定義2（同一BoundaryOffset、
「全ポート」か「一部のポート対」かは当時未分化）。隠密は`NetlistBuilder`148-158行目の一次ソース
検算で「Boundary一致・Row不一致でも縮退しうる」ことを確認し侍の主張を支持したが、
**「実運用パーツ・GuiEcad原本に同構造は実在せず杞憂」（5.1節）という留保も併記していた**。

その後、侍が`NetlistBuilder.Build`を実走させた実測（ケース5＝3ポート中2つのみ同一境界、
`L(row=0,boundary=0)`・`M(row=1,boundary=2)`・`N(row=-1,boundary=2)`）で**実害なし**と判明。
`pl`は最小`Boundary`（=L, boundary=0）、`pr`は最大`Boundary`のうち最初に見つかった方（M,Nとも
boundary=2でタイだが`>`の厳密不等号ゆえ先に見つかったMが残る）。**pl≠prゆえ縮退せず**、
Nの座標は「多端子の中間ポート、座標一致で自動結線」（`NetlistBuilder`143行目コメント）として
正常に扱われる。**「一部のポート対が同じBoundary」では実害は生じず、「全ポートが同じBoundary」
（=最小と最大が一致=全部同値）の場合にのみ`pl==pr`となり縮退する、というのが正確な実害条件**
だった。**隠密が「`||`実装だと過検出になる」と釘を刺した観点が、まさにこの実測で境目を突かれた
形になる**——検証Bの条件を「2点一致」ではなく「全ポート一致」に絞ったことで、この過検出は
構造的に防がれる。

### 1.3 設計方針の申し送り（侍への提案、拘束ではない）

- **検証A・検証Bは独立した2つの判定関数として実装することを推奨する**（`samurai.md`
  「『テストしにくい』は設計の匂い」節と同じ理由でCore層の純粋関数、`PartOptimizer.ClampPortsToFrame`
  と同じ`Ecad2.Core`層を推奨）。名前・シグネチャ・配置場所は**侍の裁量**。
- 本書は以下、検証Aを仮に`HasDuplicatePorts(IReadOnlyList<PortDef>) : bool`、検証Bを仮に
  `AllPortsShareSameBoundary(IReadOnlyList<PortDef>) : bool`（**ports.Count < 2 のときは false**、
  1.2節家老裁定1）と表記する。実装が異なる形を取る場合、侍がテストの表現形だけ読み替えてよい
  （**観点・境界値そのものは省かず実装する**こと）。
- **呼び出し位置はクランプ直後・`OrderBy`より前を推奨**。検証A・Bとも判定結果は`OrderBy`の
  前後で変わらない（4.3節）。

## 2. テスト設計技法の適用

- **検証A・検証Bは別々の判定ロジックであり、それぞれ独立に同値分割・境界値分析・対称性チェックを
  適用する**（一方の観点だけでは他方の穴を拾えない——本件がまさにその実例：検証Aだけでは
  ケース5型の実害を見逃し、逆に検証Bを「2点一致」で実装すると過検出を生む）。
- **同値分割・境界値分析**：入力ポート数（0/1/2/3個以上）と、一致パターンを分割し、境界
  （クランプ上限ちょうど・上限+1、下限ちょうど・下限-1）を明示的に狙う。
- **対称性・退化性チェック（PR-27）**：検証Aは`RowOffset`と`BoundaryOffset`の2成分一致を見る
  処理であり、`&&`/`||`の取り違えが懸念点。「Row一致・Boundary不一致」「Row不一致・Boundary
  一致」という片方の軸だけ一致するケースを対で用意する。検証Bは単一成分（`BoundaryOffset`のみ）
  の全件一致を見る処理であり、**「一部が一致」と「全部が一致」の混同**が最大の懸念点
  （ケース5がまさにこれ）。
- **既存回帰テストとの整合**：`PartOptimizerClampPortsTests`と同じ流儀で、RowOffset・
  BoundaryOffsetには区別しやすい値を使う。
- **Theory活用**：グループA・グループC（判定ロジック単体）は`[Theory]`+`[InlineData]`推奨。
  グループB（クランプとの統合）は`[Fact]`個別推奨。

## 4. 実装への申し送り・注記

### 4.1 拒否のUI表現（View層）は静的レビューで代替

`PartEditorDialog.OkButton_Click`のワイヤリング自体は、既存の「名前必須」「幅高さ範囲」
「ポート2点未満」検証と同型であり単体テストが存在しない（View層STA依存）。**本件も同型に倣い、
View層のワイヤリングは隠密の静的レビューで目視確認する**方針とし、単体テストは検証A・B双方の
Core層判定ロジックに絞る（`samurai.md`「『テストしにくい』は設計の匂い」節の教訓）。

### 4.2 グループA-9（検証A・2組の完全一致ペア）について

判定関数が「1件見つかった時点でtrueを返し打ち切る」実装でも、A-9はA-7と区別できずtrueに
しかならない。**判定がbool一戻り値である限り実害のない設計依存**と判断する。

### 4.3 呼び出し順序の検算（`OrderBy`との独立性）

検証A・B双方とも、集合の要素の値だけを見る処理であり順序に依存しない。`OrderBy`は要素を
並べ替えるだけで値の組み合わせ自体は変えないため、専用の回帰テストは不要と判断する（`onmitsu.md`
PR-27の教訓に鑑み、これは機械的確認ではなく机上の判断である旨を明記する）。

### 4.4 RED先行証明について（検証A・Bそれぞれで成立させること、家老指摘の狙い撃ち観点）

新規機能ゆえRED先行証明【MUST】の対象外だが、境界値・退化入力のテストは実装ガードを一時的に
壊すとREDになることの確認を推奨する（PR-27）。**本件は検証A・Bという独立した2つのロジックを
持つため、それぞれについて個別にRED証明の実測を行うこと**——例えば：
- 検証Aの`&&`を`||`に変えるとA-4・A-5がRED（旧実装＝検証Bを持たない状態でも検証A単体のRED証明
  としては成立するが、**旧コード（検証A・B新設前）でC-1・B-5・B-8が「保存を許可してしまう」
  ことがREDとして実測できるか**が最重要——検証Bが無ければP-129の実害ケースがそのまま通って
  しまうことの実測的裏付けになる）。
- 検証Bを「2点一致」（誤実装、`Any`で2つのペアの一致を見る形）にすると C-5・B-9 がRED（true
  になってしまう）になることを確認する——**この実測こそが、家老・侍の実測で発見した過検出を
  今後も塞ぎ続けることの証明**になる。

### 4.5 分岐F（ドラッグ時の重複、殿裁定で踏襲済み）との整合性

**衝突しないと判断する**。`docs/ecad2-t068-increment3-design-onmitsu.md`289-294行目の分岐Fは
「編集中のドラッグ操作時にチェックをしない」という設計判断であり、「保存を許可する」という
意味ではない。既存の「ポート2点未満」検証も同様に「編集中は自由・保存時に検証」という構造を
持つ。ゆえに新設の検証A・Bは分岐Fの既存設計と論理的に矛盾しない——分岐Fで生じた重複を保存時に
検出する自然な後段チェックの関係にある。B-4がこの整合性の回帰確認を兼ねる。

### 4.6 `NonSimulated`ロールの扱い（家老裁定2＝除外しない、確定）

隠密の所見「ポート数下限の除外（既存『2点未満』検査）と座標重複の除外は別軸」を家老が採用、
**検証A・Bいずれからも`NonSimulated`を除外しない**ことで確定した。B-10がこの回帰確認を担う。
根拠：`NonSimulated`要素は`PartResolver.CreatesComponent`＝falseゆえ`NetA`/`NetB`の直接的短絡は
生じないが、`hasPorts[i]`が真であれば横配線union経由のネット統合異常は理論上残るため、除外しない
方が安全側に倒れる。
