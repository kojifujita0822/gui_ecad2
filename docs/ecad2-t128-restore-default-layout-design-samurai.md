## 1. 現状の構造（一次ソースで確認）

レイアウトには**3つの層**がある。混同すると設計を誤るため、まず明確にする。

| # | 層 | 実体 | 生成のタイミング |
|---|---|---|---|
| 1 | **XAML初期状態** | `MainWindow.xaml`の`DockWidth`等 | ビルド時に固定 |
| 2 | **ハードコード既定**（メモリ上） | `_defaultDockingLayoutXml` | 起動直後に層1を`XmlLayoutSerializer`でキャプチャ（`SerializeDefaultDockingLayouts()`、コンストラクタ183行） |
| 3 | **保存済みカスタム**（ディスク） | `%AppData%\Ecad2\docking-layout\main-layout.xml` | `Ctrl+Alt+S`／**アプリ終了時に自動保存**（`Window_Closing`1418行） |

### 1.1 起動時の流れ

```
コンストラクタ 183行  SerializeDefaultDockingLayouts()   → 層2を層1からキャプチャ
コンストラクタ 186行  LoadDockingLayoutFromFileIfExists() → 層3があれば適用（層1を上書き）
```

**層2のキャプチャは層3の適用より前**に行われる（184-185行の既存コメントにも「順序が重要」と明記されている）。
ゆえに**層2は保存ファイルの有無に関わらず、常に純粋なXAMLの姿を保っている**——
これが本機能を安く実装できる根拠であり、**新しい機構を一切要さぬ理由**である。

### 1.2 なぜ `Ctrl+Alt+R` では戻せぬのか

`ResetDockingLayoutToDefault()`（724-731行）は**層3があれば層3を適用**し、無いか壊れている場合にのみ層2へフォールバックする。

**これは欠陥ではなく意図的な設計である**（T-058増分4・殿裁定(4)、716-717行のコメントに明記。隠密がT-127レビューで
`docs/ecad2-t058-increment4-review-onmitsu.md`18行目からも裏取り済み）。
現行`Ctrl+Alt+R`の位置づけは「工場出荷状態へ戻すボタン」ではなく、
**「保存済みカスタムレイアウトを保護しつつ、破損時のみ既定へフォールバックする復旧機能」**である。

案(B)はこの裁定に手を触れぬため、**既存の操作感は一切変わらぬ**。

## 2. 実装の中身

### 2.1 処理の本体

層2を適用するだけでよい。

```csharp
// T-128(殿裁定2026-07-27): 保存済みカスタム(層3)を一切見ず、出荷時のハードコード既定(層2)へ戻す。
// ResetDockingLayoutToDefault(Ctrl+Alt+R)が層3を優先するのは殿裁定(4)による意図的な設計ゆえ、
// そちらには手を触れず別経路として設ける。
private void RestoreFactoryDefaultDockingLayout()
{
    if (_defaultDockingLayoutXml is not null)
        TryDeserializeDockingLayout(_defaultDockingLayoutXml);

    // Deserialize直後はタイトルが焼き付け時点の初期値へ戻るため、状況依存タイトルを再同期する
    // (T-058増分3の隠密指摘1と同型。既存2経路と同じ後始末)。
    UpdateOutputPanelTitle();
    UpdateRightPanelBottomTitle();
    _viewModel.StatusMessage = "パネルレイアウトを既定に戻しました";
}
```

`_defaultDockingLayoutXml`が`null`になるのはコンストラクタが途中で失敗した場合のみで、
その状況では既にアプリが立ち上がっておらぬ。実質フォールバック不要だが、既存2経路と同じく`null`ガードは置く。

**ステータス文言の重複に注意**——既存`ResetDockingLayoutToDefault()`は
「パネルレイアウトを既定に戻しました」を出す。両者が同じ文言では区別が付かぬため、
どちらかを改める必要がある（4.4節）。

## 3. 責務の切り分けと rule of three（DoD 4への答え）

### 3.1 3経路の責務

| メソッド | 責務 | 適用する層 | 入口 |
|---|---|---|---|
| `LoadDockingLayoutFromFileIfExists()` | 起動時の復元 | 層3（無ければ何もせず層1のまま） | コンストラクタ |
| `ResetDockingLayoutToDefault()` | **保存済みカスタムへの復旧**（現状維持） | 層3（破損時のみ層2へ） | `Ctrl+Alt+R` |
| **`RestoreFactoryDefaultDockingLayout()`**（新設） | **出荷時既定への復帰** | **層2のみ**（層3を一切見ない） | 新設メニュー項目 |

**案(B)ゆえ既存2関数には手を入れぬ**のが基本方針。新設関数は`_defaultDockingLayoutXml`フィールドを
直接読み、既存の`TryDeserializeDockingLayout`（IO/XML構文/Content実体欠落の3層保護つき）と
`RebindDockingContent`をそのまま再利用する。**新しい機構は要らぬ。**

### 3.2 【要相談】層2へのフォールバックが3箇所目に達する

`if (_defaultDockingLayoutXml is not null) TryDeserializeDockingLayout(_defaultDockingLayoutXml);`
という2行は、**既に2箇所に存在する**（`LoadDockingLayoutFromFileIfExists`705-706行、
`ResetDockingLayoutToDefault`729-730行）。新設で**3箇所目＝`samurai.md`「共通ロジックの複製検知」
（PR-07、rule of three）に到達する**。

同節は「3箇所目の複製に気づいたら家老へ一報し共通化の要否を相談する」と定めているため、ここに記す。

| 案 | 内容 | 利点 | 難点 |
|---|---|---|---|
| **ア（侍の推奨）** | **共通化せず、3箇所のまま置く** | 案(B)の趣旨「既存2関数に手を入れぬ」を守れる。既存2関数はいずれも殿裁定が絡む繊細な箇所で、触れば回帰の危険が生じる | 4箇所目が出れば必ず共通化が要る |
| イ | `TryApplyFactoryDefaultLayout()`のような小さなヘルパーへ括り、3箇所から呼ぶ | 定義が1箇所に集まる | **既存2関数に手を入れることになる**。T-128の範囲を越える |

**推奨がアである理由**——複製されているのは「nullガード＋既存メソッド呼び出し」の2行のみで、
**判断ロジックを含まぬ**。PR-07が防ごうとしているのは「複製箇所の一部だけ修正され取りこぼす」事故だが、
本件はロジックを持たぬため、その事故が起きる余地が乏しい。それよりも殿裁定の絡む既存関数へ
不要に触れる方が危うい、と見る。**ただし判断は家老に仰ぐ。**

## 4. 殿のご判断を仰ぐ事項

### 4.1 【要判断1】メニューバーのどこに置くか

既存のメニュー構成は「ファイル(_F)／編集(_E)／図面(_D)／表示(_V)／ツール(_T)／パーツ(_P)／ヘルプ(_H)」の7つ。
**レイアウト関連の項目はすべて「表示(_V)」配下に集まっている**（「パネルを自動的に隠す」「配置ツールバーを
フロート化」「現在のレイアウトを既定として保存」）。

| 案 | 置き場所 | 利点 | 難点 |
|---|---|---|---|
| **ア（侍の推奨）** | **「表示(_V)」直下**、既存の「現在のレイアウトを既定として保存(_L)」（951行）の**すぐ下** | レイアウト操作が一箇所にまとまる。「保存する」と「戻す」が隣り合い対をなす。変更が最小 | 「表示」メニューの項目が1つ増える（現在6項目→7項目） |
| イ | 「表示(_V)」配下に**「レイアウト(_Y)」サブメニュー**を新設し、「保存」「既定に戻す」を収める | 将来レイアウト関連が増えても整理が保たれる | **既存項目（保存）を移動することになり、殿の操作の記憶が変わる**。今は2項目しかなく、階層を作るほどでもない |
| ウ | 「ツール(_T)」配下 | 「設定・保守」の色合いで括る見方もある | 既存のレイアウト項目と離れ、探しにくくなる。「ツール」は設計チェック・テストモードという図面操作の場 |

**アクセスキー**——「表示(_V)」配下の使用済みは`_G`（グリッド表示）・`_D`（ダークモード）・`_A`（パネルを
自動的に隠す）・`_F`（配置ツールバーをフロート化）・`_L`（現在のレイアウトを既定として保存）。
**`_R`は空いており、「既定レイアウトに戻す(_R)」がそのまま使える。**

**メニュー項目の文言案**（表記は殿裁定により「既定」で確定）：

| 案 | 文言 | 備考 |
|---|---|---|
| **A（侍の推奨）** | **「既定レイアウトに戻す(_R)」** | 殿の仰せ「既定のレイアウトに戻す」をほぼそのまま。簡潔 |
| B | 「パネルレイアウトを既定に戻す(_R)」 | 対象がパネルであることが明確。既存ステータス文言とも揃う。やや長い |
| C | 「レイアウトを既定に戻す(_R)」 | 中間 |

**なお残る論点**：初版で提起した「既存`Ctrl+Alt+R`もメニューへ露出させるか」は、殿裁定が案(B)ゆえ
**本設計では採らぬ**。ただし`Ctrl+Alt+R`が引き続きメニューに現れぬままである点は事実として記しておく
（殿が後日「保存したレイアウトへ戻す」操作も画面から辿りたいとお考えになれば、別途起こす筋のもの）。

### 4.2 【要判断2】確認ダイアログの要否

現在のパネル配置が失われる操作である。**要否そのものが殿の裁可事項**ゆえ、両案の理を示す。

| 案 | 内容 | 理 |
|---|---|---|
| **ア（侍の推奨）＝確認なし** | 押すと即座に戻し、ステータスバーへ結果を出す | (1)**図面データには一切触れぬ**——失われるのはパネルの配置のみで、戻した後にユーザーが自分で動かし直せる (2)既存の`Ctrl+Alt+R`も確認なしであり、**同種の操作で作法が揃う** (3)後述4.3節(i)を採れば、**直後に`Ctrl+Alt+R`を押すことで元のカスタム配置へ復帰でき、実質的な取り消しになる** |
| イ＝確認あり | 「現在のパネル配置は失われます。よろしいですか」等 | (1)メニューの押し間違いへの備え（隣接する「現在のレイアウトを既定として保存」と1つ違いで並ぶ） (2)手間をかけてパネルを整えた殿にとっては、配置も惜しい成果物である |

**侍の推奨がアである最大の理由**は、4.3節(i)と組み合わさると**取り消しの道が残る**点にある。
逆に4.3節(ii)を採るならば、取り消しが効かなくなるため**確認ありのイと組み合わせるのが釣り合う**。
**この2つの判断は連動する**ことを申し添える。

### 4.3 【要判断3】保存ファイルの扱い

**まず事実として——削除も明示保存も「必須ではない」。** `Window_Closing`（1418行）が
`SaveDockingLayoutAsDefault()`を無条件に呼ぶため、**既定へ戻した状態でアプリを終了すれば、
その姿がそのまま`main-layout.xml`へ書き込まれる**。次回起動時も既定のまま立ち上がる。

| 案 | 挙動 | 利点 | 難点 |
|---|---|---|---|
| **(i)（侍の推奨）終了時の自動保存に任せる** | 戻すだけ。ファイルは終了時に更新される | **取り消しの道が残る**——戻した直後に`Ctrl+Alt+R`を押せば、ファイルにまだ残る元のカスタム配置へ復帰できる。操作も軽い | アプリが異常終了した場合、古いカスタムが残る（次回起動時に元へ戻る） |
| (ii) 戻すと同時に明示保存 | 直後に`SaveDockingLayoutAsDefault()`を呼ぶ | ユーザーの意図が即座に永続化され、異常終了にも耐える | **取り消しの道が閉ざされる**（`Ctrl+Alt+R`の戻り先が既に上書き済みになる）。4.2節イ（確認あり）とセットにするのが釣り合う |
| (iii) ファイルを削除 | `main-layout.xml`を消す | 状態が最も単純 | **破壊的操作**。`rm`禁止【MUST】の趣旨に反する。**採らぬ** |

家老は(ii)を「破壊的操作を避けられる」と見立てておられ、その通り(iii)よりは穏当である。
**それがしはさらに一歩進めて(i)を推す**——**(i)は破壊的でないばかりか、取り消しの道まで残る**からである。

### 4.4 【要判断4・軽微】ステータスバーの文言

既存`ResetDockingLayoutToDefault()`は「パネルレイアウトを既定に戻しました」を出す。
新設分が同じ文言では、どちらが働いたのか区別が付かぬ。

| 案 | 新設分の文言 | 既存`Ctrl+Alt+R`の文言 |
|---|---|---|
| **ア（侍の推奨）** | 「パネルレイアウトを**出荷時の既定**に戻しました」 | 現状維持（「パネルレイアウトを既定に戻しました」） |
| イ | 「パネルレイアウトを既定に戻しました」（同一） | 現状維持 |
| ウ | 「パネルレイアウトを既定に戻しました」 | **「保存したレイアウトに戻しました」へ改める** |

案ウは既存の挙動をより正確に言い表すが、**既存文言に手を入れることになる**（案(B)の趣旨から外れる）。

## 5. 規模・リスク・テスト方針

### 5.1 規模

| 対象 | 内容 | 規模 |
|---|---|---|
| `MainWindow.xaml` | 「表示(_V)」メニューへ項目1つ追加（951行の直下） | 1〜2行 |
| `MainWindow.xaml.cs` | `RestoreFactoryDefaultDockingLayout()`＋メニューハンドラ1つ | 15行程度 |

**小規模。** 既存の仕組み（層2のキャプチャ・`TryDeserializeDockingLayout`・`RebindDockingContent`）が
そのまま使えるため、新しい機構は一切要らぬ。

### 5.2 リスク

- **低い**。層2は起動時に必ずキャプチャされ、内容はXAMLの姿そのもの。適用経路も既存2経路と同一
- **既存2関数に手を入れぬ**ため（3.1節）、`Ctrl+Alt+R`・起動時復元への回帰の恐れが構造的に無い
- **留意点＝Deserialize直後のタイトル再同期**（2.1節）。忘れるとT-058増分3で隠密が指摘した
  「タイトルだけ既定値へ巻き戻り中身と食い違う」欠陥を再び作り込む。既存と同じ後始末を必ず置く

### 5.3 テスト方針

`MainWindow`のコードビハインドはView層（STA依存）であり、既存のレイアウト系メソッドにも単体テストは無い。
**本件も同型に倣い単体テストは設けず、隠密の静的レビューと忍者の実機確認に委ねる**
（`samurai.md`「『テストしにくい』は設計の匂い」節に照らしても、ここは純粋関数へ切り出せる計算が無く、
AvalonDockのレイアウト木を操作する処理そのものである）。

**忍者の実機確認の観点（案）**：
1. 保存済みレイアウト（左パネル幅が既定と異なる状態）を作り、メニューから既定へ戻ることを確認
2. 戻した直後の左パネル幅がXAMLの値（現行190px）と一致すること
3. **そのまま終了→再起動で既定のまま立ち上がること**（4.3節(i)の裏取り）
4. **既存`Ctrl+Alt+R`が従来どおり「保存済みカスタムへ戻す」挙動を保っていること**（案(B)の要）
5. **戻した直後に`Ctrl+Alt+R`を押すと元のカスタム配置へ復帰すること**（4.3節(i)＝取り消しの道の裏取り。
   ただし4.3節(ii)が採られた場合は逆に「復帰しないこと」を確認する）
6. パネルをフロート化・オートハイド化した状態からも戻せること

**検体**：忍者の控え`C:\ECAD2\sample\t127-layout-backup\main-layout.xml.bak-20260727`
（書き換え前の原本＝左パネル220pxの状態）がそのまま使える。

## 6. P-132との関係

P-132＝「XAMLの既定値を変えても保存値が勝つ構造の根治（既定値変更時に自動追随する仕組み）」は
**本タスクの射程外**である。本件はあくまで「**ユーザーが自力で既定へ戻す手段**」を与えるもの。

ただし**本機能があれば、P-132の実害はユーザーの手で解消できる**——アプリ更新でXAMLの既定値が
変わった際、「既定レイアウトに戻す」を一度実行すれば新しい既定が適用される。
**P-132の根治は「ユーザーが操作せずとも追随する」ことを目指すものであり、本件はその前段として
「操作すれば追随できる」状態を作る**、という関係にある。
