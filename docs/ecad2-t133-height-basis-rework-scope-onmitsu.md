## 0. 題目

殿の御言葉＝「やはりユーザー目線で考えると設定値と見た目の差異が大きい。手戻り規模を算定して」。対象＝自作部品の高さ基準を、現行の殿裁定11（H-2＝中心基準・高さhは`2h-1`セルを占める）から、H-3（上端基準・高さhは`h`セルを占める）へ変える案の規模算定。

**先に結論の要約**——
- **DoD1**：手が入るのは主に4層＝(a)Core層の幾何算出2箇所（`FrameRect`・`ClampPort`）(b)main診断側の占有判定1箇所（`ElementInstance.RowSpan`系）(c)T-137の区切り線2箇所（`GridLineXs`/`GridLineYs`のうちY側）(d)関連ドキュメント・コメント多数。**規模は「中」——単一の定数変更ではなく、複数箇所の式の形自体が変わる**。
- **DoD2**：既存テストは**推計40〜55件程度が影響を受ける**。うち**名前・入力データごと書き直しが要るもの（中心基準を明示する名前・対称データを使うもの）が半数程度、期待値のみの変更で済むものがもう半数程度**。
- **DoD3（最重点）**：**既存の自作パーツデータ（現に3件が実在）は、単純な値の付け替えでは解釈が変わってしまう。高さの意味そのものが変わる（`2h-1`→`h`）ため、同じ`heightCells`値のままでは既存の外周ポート位置を保持できない。** 詳細は3節。
- **DoD4**：T-136(A)増分1（`SheetAffinity`）は高さ・行基準に一切依存しておらず、**直接の波及なし**。
- **DoD5**：**原本GuiEcadは「H-2」でも「H-3」でもない第3の形**であった——**中心基準・高さ=h セル（`2h-1`ではない）**。ecad2のH-2はP-148裁定で独自に導入された拡張であり、H-3は原本の「中心基準」という性質も変える案である。詳細は5節。

## 1. DoD1：どこに手が入るか

### 1-1. Core層（幾何の算出そのもの）

| 箇所 | 現行（H-2） | H-3で変わる形 |
|---|---|---|
| `PartShapeGeometry.FrameRect`（`:98-109`） | `Y = -((h-1)+0.5)*cellMm`、高さ`(2(h-1)+1)*cellMm=(2h-1)*cellMm` | 上端基準なら`Y`は`h`に依らぬ固定値（例：`-0.5*cellMm`）、高さは`h*cellMm`——**式の形自体が変わる（単純な係数変更ではない）** |

**この2箇所は「単一定数の書き換え」では済まぬ**——戻り値の計算式そのものが対称形から非対称形へ変わる。

### 1-2. Core層（main図面側の占有判定＝殿裁定11の本体）

### 1-3. T-137の区切り線（本日実装）

`PartShapeGeometry.GridLineYs`（`:147-157`）は`FrameRect`の高さから逆算しているため、**`FrameRect`が変われば`GridLineYs`の呼び出し側の挙動も追随して変わる**。ただし`GridLineYs`自体のロジック（「半整数の位置を範囲内で返す」）は基準に依らず正しく動く見込みで、**関数自体の書き換えは不要、期待値のみが変わる**——境界線の本数が`2h`本から`h+1`本へ変わる（h=2なら4本→3本）。

## 3. DoD3（最重点）：既存の部品データの解釈は変わるか

### 3-1. 現に存在する自作パーツファイルを実地に確認した

`docs-notes/handover-next-session.md`に記載の検体3件（`T133INC1H2`・`T133INC1H3`・`T133P148H3`、実体は`OneDrive\ドキュメント\Ecad2\図形\自作\`）の中身を直接読んだ。

| ファイル | `heightCells` | `ports`の`rowOffset` |
|---|---|---|
| `T133INC1H2.gcadpart` | 2 | **-1, 0, 0, +1**（4ポート中3種のrowOffset） |
| `T133INC1H3.gcadpart` | 3 | **-2, 0, 0, +2** |
| `T133P148H3.gcadpart` | 3 | **-2, 0, 0, +2** |

**いずれも高さ設定の許す最大範囲（`±(h-1)`）いっぱいまでポートを置いた検体**であり、机上の懸念ではなく**現に実在するデータで問題が起きる**ことを確認した。

### 3-2. なぜ単純な値の付け替えでは済まぬか

H-3（高さh＝hセル占有、`rowOffset∈[0,h-1]`）へ移った場合、**同じ`heightCells`値のまま**では：
- `T133INC1H2`（h=2）の`rowOffset=-1`は、新しい許容範囲`[0,1]`に**入らぬ**（負値を許さぬため）
- `T133INC1H3`・`T133P148H3`（h=3）の`rowOffset=-2,+2`も同様に、新しい許容範囲`[0,2]`に入らぬ

**これは「基準点をずらすだけ」の変換では解決しない**——なぜなら、H-2の`h=2`は物理的に3行分（`2h-1`）を使うのに対し、H-3の`h=2`は2行分しか使わぬため、**同じ`heightCells`値では物理的な行数の器そのものが縮む**。既存データの3行分（`rowOffset=-1,0,+1`）をそのまま活かすには、**`heightCells`の値自体を`2h-1`（この場合h=2→3、h=3→5）へ書き換え、かつ`rowOffset`を`旧値+(旧h-1)`だけ加算して非負域へ平行移動する、という2段階の変換（データマイグレーション）が要る**。

**マイグレーションを行わずロード時に何もしなければ**——`heightCells`はそのまま残り（永続化層はただの`int`を読み書きするのみで量子化・再解釈は行わぬ、T-136A調査で確認済みの流儀と同じ）、**ファイルの中身自体は変化しない**。ただし`ClampPort`が新しい範囲`[0,h-1]`でしか丸めなくなるため、**次にパーツエディタでこのファイルを開き、既存ポートを1つでも動かす（ドラッグ等）と、`ClampPort`が新しい範囲へ強制的にクランプし直し、ポートの位置が動いてしまう**（T-138のスナップ刻み調査で確認した「移動は差分加算ゆえ既存頂点を動かさぬ」性質とは別の経路——`ClampPort`はドラッグの都度、絶対座標を新しい範囲へ丸め直す実装であり、差分加算ではない。`PartEditorCanvas.cs:456,472`参照）。

**→ 結論**：**ファイルを開くだけなら中身は変わらぬが、開いて何か1つでもポートを操作した瞬間に、外周のポート（`T133INC1H2`の`-1`・`+1`、`T133INC1H3`等の`-2`・`+2`）は新しい範囲へ吸着され、電気的な意味を持つ座標が動く恐れがある**。安全に移行するには、上記のマイグレーション（`heightCells`と`rowOffset`を同時に書き換える）を伴う専用の対応が要る。

### 3-3. 実害の現状範囲——**限定的**

3件の検体はいずれも**T-133/T-136検証専用の残置ファイル**（`docs-notes/handover-next-session.md`記載どおり、増分4の検証に使うため意図的に残されたもの）であり、**現時点でいずれのシートにも配置されていない**（`OneDrive\ドキュメント\Ecad2\`直下の他のファイルを確認したが、シート・図面データは見当たらず、パーツライブラリ単体のファイルのみ）。**また組込み15件のテンプレート（`a接点`等）はすべて`heightCells=1`であり、本件の影響を受けぬ**（`grep`で確認済み）。**ゆえに「既に配置された要素の接続が電気的に変わる」という最悪の実害は、現時点では発生しておらぬ**。ただし、**もし将来この種の高さ≥2の自作パーツが実際にシートへ配置された後にH-3へ移行すれば、配置済み要素の接続点位置が動き、結線が変わる恐れがある**——今回はその手前の段階で気づけた形である。

## 5. DoD5：原本GuiEcadはどちらの基準か——**H-2でもH-3でもない第3の形**

原本ソース（`C:/Users/kojif/Desktop/生産物/gui_ecad/src/GuiEcad.App/PartEditorWindow.xaml.cs`）を直読した。**予想外の事実が見つかったため、事実を正確に区切って報告する。**

### 5-1. 原本のフレームは「中心基準・高さ=hセル」——H-2の`2h-1`とは違う

```csharp
private double Sy(double cy) => _originY + (cy + _h / 2.0) * _cellPx;   // :196
...
ds.DrawRectangle((float)Sx(0), (float)Sy(-_h / 2.0), (float)(_w * _cellPx), (float)(_h * _cellPx), frame, 1.5f);  // :265
```

**フレームは`y∈[-h/2, +h/2]`、高さ＝`h`セルちょうど**（`_h`は殿が入力するそのままの設定値、`:189` `Math.Clamp(...,1,12)`）。**`2h-1`という拡張はここには無い**——**原本は「設定値がそのままセル数になる」という、まさに今回殿が求めておられる直感と一致する形であった。**

### 5-2. ただしポートの可動域は`±(h-1)`——ecad2のClampPortと同じ形

```csharp
int rowOff = Math.Clamp((int)Math.Round(local.Y), -(_h - 1), _h - 1);   // :616, :627
```

**h=2なら`rowOff∈{-1,0,1}`の3通り**——これは**フレーム（2セル、`y∈[-1,+1]`）の外周ちょうどに、半セルの余裕なくポートが乗る**ことを意味する（フレーム上辺`y=-1`とポート`rowOff=-1`の位置`y=-1`が一致）。**ecad2のP-148裁定（フレームを`2h-1`セルへ広げ、ポートに半セルの余裕を持たせる）は、原本のこの「余裕の無さ」を解消するために独自に加えられた拡張であった**、と見受けられる（P-148の経緯を記した既存文書に「原本にもある不一致を承知のうえで揃える道」という記述があり、本調査の所見と符合する）。

### 5-3. 【重要な限定】原本のmain図面には、そもそも高さ≥2の占有という概念が無い

`_h`はあくまで**パーツエディタ内でのフレーム描画・ポート可動域の話**であり、**原本のmain図面（ラダー図面本体）には`ElementInstance`の高さプロパティ自体が存在せず**（本セッション既出の所見どおり）、**「高さhの部品が図面上で何行を占有するか」という問い自体が原本に存在しない**。ゆえに**殿裁定11（占有行の基準）は、そもそも原本に前例のないecad2独自の概念であり、「原本ではどちらか」という問いは、パーツエディタのフレーム描画に限っては答えられるが、main図面の占有についてはそもそも比較対象が無い**。

### 5-4. DoD5への答え

**原本はH-2（`2h-1`セル・対称）でもH-3（上端基準・hセル）でもない、第3の形＝「中心基準・hセルちょうど」であった。** **H-3案（上端基準）は、原本の「中心基準」という性質からも離れる**——**もし原本回帰を志向するなら、むしろ「中心基準のまま`2h-1`をやめて`h`セルに戻す」案（本書ではH-2/H-3いずれとも異なる第4の案となる）も検討の俎上に載りうる**、と隠密は見立てる（推測、事実と分けて記す。採否は殿・家老の領分）。

**なお`karo.md`【MUST】「『欠陥』と判定する前に原本・設計意図の確認を指示する」に照らせば**——**現行のH-2（`2h-1`）は「移植の誤り」ではなく、P-148裁定という殿ご自身の意思決定を経た拡張**であり、**原本から離れた点は事実だが、それ自体は正当な経緯を持つ**。
