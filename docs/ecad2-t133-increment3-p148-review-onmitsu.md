## 所見1【要判断・最重】自作パーツ（PartId経路）の高さが、どの増分にも割り当てられておらぬ

### 事実

- `PlaceElementAtSelectedCell`（`MainWindowViewModel.cs:2996-3022`）は
  **幅のみ** `PartLibrary.Get(partId)?.WidthCells ?? 1` から取り（`:3001`）、
  **高さは `cellHeight: 1` 固定**（`:3005`）。生成する `ElementInstance` にも
  `CellWidth` のみ設定し `CellHeight` は設定せぬ（`:3016-3022`）
- `PartDefinition.HeightCells` は**存在し既定1**（`PartDefinition.cs:54`）。
  パーツエディタで設定でき（`PartEditorCanvas.cs:676` が `_heightCells` を `FrameRect` へ渡す）、
  GuiEcad原本の `HeightBox` は `Math.Clamp(..., 1, 12)` で **h=12 まで許容**
  （`ecad2-p148-frame-portrange-mismatch-options-onmitsu.md:60`）
- 侍のコメント（`:3002-3004`）は
  **「高さを持つ要素を置くのは増分4で新設する Kind 経路であり、そちらが `DefaultCellHeight` から取って渡す」**と述べる
- **しかし増分4の計画（`ecad2-t133-implementation-plan-samurai.md:258`）に高さの語は無い。**
  **PartId 経路の `HeightCells` 反映は、増分0〜9のどこにも記述が無い**（未割当）
- **必要性は既に指摘されておった**——
  `ecad2-t133-height-and-port-pitch-survey-onmitsu.md:161`
  「そのままでは高さの供給源にならぬ——`HeightCells` を読む分岐の追加が別途要る」／
  `ecad2-t133-plan-b-scope-estimate-samurai.md:111-115`（**侍自身が全使用箇所を列挙して確認しておる**）

### 判定

**増分3の実装の瑕疵ではない。** 挙動を変えぬのが増分3の目的にて、現状維持は正しい。
**これは計画の穴（未割当）と、コメントの射程超過にござる。**

`ElementCatalog.DefaultCellHeight(ElementKind)` は**組込み種別用**であり、
自作パーツは `PartDefinition.HeightCells` という**別系統**。
**増分4で Kind 経路に高さが入っても、この経路の穴は残る。**

**対処は `Math.Max(0, ... - 1)` を3箇所＝1行ずつゆえ安い。**

## 所見6【確定】`ClampPort` との整合を一次ソースで検算

- `ClampPort`（`PartShapeGeometry.cs:110-111`）＝`rowLimit = Math.Max(0, h-1)`、row ∈ `[-rowLimit, +rowLimit]`
- **接続点の描画Y＝`RowOffset * CellMm`**（`PartEditorCanvas.cs:697` → `:231` `CellToLocalMm`）
  ——**テストのコメントが置く前提を、一次ソースで裏付けた**
- 枠 Y ∈ `[-(rowLimit + 0.5) * cellMm, +(rowLimit + 0.5) * cellMm]`
  → **余裕は常にちょうど半セル。h=1, 2, 3, 5, 12 すべてで一定**

テスト期待値を手計算で全件突合し、**一致**——

| 入力 | 半径の計算 | 期待値 | 判定 |
|---|---|---|---|
| `(3, 5, 2.5)` | `(5-1+0.5)*2.5 = 11.25` | 高さ22.5・Y=-11.25 | ✓ |
| `(5, 3, 2.0)` | `(3-1+0.5)*2.0 = 5.0` | 高さ10.0・Y=-5.0 | ✓ |
| `(1, 4, 3.0)` | `(4-1+0.5)*3.0 = 10.5` | 高さ21.0・Y=-10.5 | ✓ |
| `h=0`（退化） | `Math.Max(0,-1)=0` → `0.5*9=4.5` | Y=-4.5・高さ9.0 | ✓ 反転せず |
| `h=1` | `0.5*9=4.5` | Y=-4.5・高さ9.0 | ✓ 旧式と一致 |

## 射程の埋め残し——本レビュー自身が、本日立てた項の射程外で同型の誤りを犯した

**事実**：本調査書の総括表は当初、所見7〜10を**1行に束ねて**おり、
家老への報告でも**「軽微4件」**と数え、概略も4つしか挙げなんだ。
**正しくは5件**（所見2・7・8・9・10）で、**所見9が落ちておった。**
**侍が本調査書を直読して食い違いを見つけ、家老の照会で露見した。**

**発生源は総括表**にござる——**所見の本体は初めから5件あり、束ねた行が数を潰した。**
peerメッセージはそれを写しただけであった。

**本日、隠密は同型の誤りへの対処として
「表と文の両方を書いたら、文の主張を表の行で1つずつ指させよ」を立て、
その射程を「表と文が同一文書にある場合のみ」と自ら区切った。**
**そして区切った射程の外で、同じ型の誤りを犯した。**

**埋め残しの所在**——区切りの際、別文書間の食い違いは
**「調査ワークフロー2項（過去の調査書から数字を引くときは一次ソースで再現してから使う）の領分」**と
書いた。**ところが同項は「過去の」調査書が対象にて、
「今しがた自分が書いた調査書を要約する」場合を射程に含んでおらぬ。**
**そこが穴であった。**

**落とし先の案（家老の判断を仰ぐ）**——`onmitsu.md`「報告フォーマット」節へ一文：

> **調査書と要約（peerメッセージ・総括表）で数を二度書いたら、二度目は一度目を数え直して書け。**
> **とりわけ総括表で複数の所見を1行に束ねる時は、束ねた中の件数を明記する。**
> **束ねた行は数を潰す。**

**この一件が示すのは、射程の区切りそのものが検算を要るということにござる**——
**区切った先（「あちらの領分」と送った先）が、本当にその穴を覆っておるかまで見ねばならぬ。**
