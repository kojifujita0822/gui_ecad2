## 0. 起草の方針

**Undoは「積む」処理ゆえ、テストの主語は3つに分かれる**——

| 主語 | 問い |
|---|---|
| **積むか** | 操作後に`CanUndo`が真になるか |
| **積まぬか** | **拒否・同値の場合に積まぬか**（積むと空のUndoが1回挟まり、使い手には「効かぬUndo」に見える） |
| **戻るか** | Undo一回で操作前へ**完全に**戻るか |

**「積むか」だけを見るテストは弱い。** 3つを対で持つのが本設計の骨格にござる。

**既存の流儀**＝`ViewModelTestBase`を継承し`CreateViewModel()`→`vm.NewDocument()`から始める
（`tests/Ecad2.App.Tests/UndoRedoCommandsTests.cs`）。**同じ流儀に揃える。**

## 1. 全6件に共通する観点（横断）

**ペア構成の対称性**（技法）＝**6件すべてに同じ行が埋まっているかを表で点検する。**
**1種で検証している観点が他種で抜ける、というT-041増分7の轍を踏まぬため。**

| # | 観点 | 期待 |
|---|---|---|
| C1 | 操作前 | `CanUndo == false` |
| C2 | 操作後 | `CanUndo == true` |
| C3 | Undo一回 | 操作前の状態へ**完全に**戻る（下記「完全に」の定義） |
| C4 | Redo | 操作後の状態へ戻る |
| C5 | **拒否・同値の場合** | **`CanUndo`が変わらぬ**（積まぬ） |
| C6 | 新規操作後 | **Redo履歴が消える**（`CanRedo == false`） |

**C3「完全に」の定義**——**件数だけを見てはならぬ**（PR-27、6節）。
**要素なら`Id`・`Pos`・`PartId`・`DeviceName`、機器表なら`Devices.ByName`のキーと`Class`まで見る。**

## 2. 件ごとの設計

### 2-1. 要素の配置（`PlaceElementAtSelectedCell`）

**状態遷移**＝`未配置 → 配置済`。**拒否経路が2つある**のが肝。

| # | 入力 | 期待 | 技法 |
|---|---|---|---|
| P1 | 空きセルへ配置 | `Elements.Count`+1、`CanUndo`真 | 代表値 |
| P2 | Undo一回 | `Elements.Count`が元へ、**`Devices.ByName`からも消える** | C3 |
| P3 | **占有済みセルへ配置** | **拒否。`CanUndo`は偽のまま** | **C5・最重要** |
| P4 | **グリッド範囲外へ配置** | 同上 | **C5** |
| P5 | 幅2パーツを右端へ（右端がはみ出す） | 拒否。積まぬ | 境界値 |
| P6 | デバイス名あり／なし | 両方で積む。名なしは機器表に触れぬ | 同値分割 |
| P7 | **既存デバイス名で配置**（新規登録が起きぬ） | 積む。**Undoで既存エントリが消えぬ** | 境界 |

**境界値（グリッド）**——`[Theory]`+`[InlineData]`で網羅する：

| 位置 | 期待 |
|---|---|
| 行0・列0 | 配置成功 |
| 行`Rows-1`・列`Columns-1` | 配置成功 |
| 行`-1`／列`-2` | **仕様範囲**（`memory: ecad2_grid_negative_range_spec`）——**配置の可否は`ValidatePlacement`の現仕様に従う。設計者は決めぬ**。**現仕様を実測して期待値を定めること** |
| 行`Rows`／列`Columns` | 拒否・積まぬ |

**【侍への注記】P3・P4は「積まぬ」ことの検証ゆえ、`RecordSnapshot`を`ValidatePlacement`より
前に置くと落ちる。** **この2件が置き場所を守る網にござる。**

## 3.【DoD 2・最重要】配置と合流先確定は一体の操作か

### 3-1. 何が起きるか（一次ソースによる事実）

`PlaceElementAtSelectedCell(partId, deviceName, isOr: true)`は——

1. `sheet.Elements.Add(newElement)`＋機器表登録（`:2931-2940`）＝**配置はここで完了しておる**
2. `if (!isOr) return;`（`:2951`）
3. 候補を作り、**`ToolMode.ConfirmOrJoinTarget`へ遷移**（`:2953-2959`）
4. **使い手がEnterを押すと`ConfirmOrJoinTarget()`が走る**（別の呼び出し）

**すなわち「1回の配置操作」が、コード上は2つのメソッド呼び出しに分かれておる。**

### 3-2. 素朴に計装すると二重に積まれる

**両方に`RecordSnapshot`を置くと、Undo履歴が2つ積まれる**——
使い手は**Enterを1回押しただけなのに、Undoを2回押さねば配置前へ戻らぬ。**
**しかも1回目のUndoで戻るのは「合流先が未確定の、宙ぶらりんな配置済み状態」**にござる。

### 3-3. 設計の分岐（**隠密は決めぬ。裁定を仰ぐ**）

| 案 | 中身 | 代償 |
|---|---|---|
| **(a)** 配置時のみ積む | Undo1回で配置前へ戻る（**使い手の直感に最も近い**） | 合流先の**選び直し**だけを戻せぬ |
| **(b)** 確定時のみ積む | 合流先まで含めて1回 | **`isOr=false`の通常配置で積まれぬ**——別途分岐が要る |
| **(c)** 両方積む | 段階的に戻せる | **3-2の二重問題**。Undo2回が要る |

**拙者の見立て＝(a)が本命**（**推測と明示する**）。**根拠**＝**配置は手順1で既に完了しており、
手順3以降は「配置済み要素をどのネットへ繋ぐか」の付随操作**にござる。
**ただし「合流先を選び直したい」という使い手の要求を潰す**ゆえ、**裁定を仰ぐ筋。**

### 3-4. どの案でも要るテスト

| # | 観点 | 期待 |
|---|---|---|
| X1 | `isOr=true`で配置→合流先確定 | **Undoの回数が裁定どおりか**（(a)なら1回で配置前） |
| X2 | `isOr=true`で配置→**Escで取消** | **積まれた回数が裁定どおりか。宙ぶらりんな状態が残らぬか** |
| X3 | `isOr=false`で配置 | **どの案でも必ず1回積まれる**（(b)を採るなら分岐の網） |
| X4 | 候補0件で`isOr=true` | **遷移せぬ**（`:2954`）。**通常配置と同じく1回** |

**X4が退化ケースの網**——**候補0件なら手順3に入らぬゆえ、(b)を採ると積まれぬ。**

## 4.【DoD 3】同値ガードの要否

### 4-1. 現状（一次ソースで確認）

| 件 | 同値ガード | 出典 |
|---|---|---|
| 3 機器名 | **有り** | `:2155` |
| 5 行コメント | **有り** | `:2613` |
| **6 文書情報** | **無し** | `:269-279`（無条件代入） |

### 4-2. 既に確立した規約がある

**「値が実際に変化する場合のみ`RecordSnapshot`」は本プロジェクトの規約**にござる——
`FindViewModel.cs:210-213`のコメント（T-070隠密レビュー指摘A-5）が理由を述べておる：

> 実際に変化するかを判定する前に`RecordSnapshot`を呼ぶと**no-op置換でも無意味な
> スナップショットが積まれ、既存のRedo履歴が消去される**

**すなわち同値で積むことの害は「空のUndo」だけでなく「Redo履歴の消失」にござる。**

### 4-3. ゆえに——**6（文書情報）には同値ガードの新設が要る**

**3・5は既存ガードの内側に`RecordSnapshot`を置けば足りる**（ガードは`return`で抜けるゆえ、
その後に置けば同値では到達せぬ）。

**6は現状ガードが無いゆえ、Undoを足すと規約に反する。**
**「ダイアログを開いて何も変えずOKした」だけでRedo履歴が消える。**

**【隠密は設計を決めぬ】** ガードを新設するか、`ApplyDocumentInfo`の外側（呼び出し元
`MainWindow.xaml.cs:1194-1195`）で比較するかは侍・家老の領分。**要ることのみ指摘する。**

**テスト**＝**I3を「積まぬ」という期待で書けば、この論点が実装で解かれたかを測れる。**

## 5.【DoD 4】Undo一回で戻る単位は直感と合うか

**3節（配置＋合流先）が最大の論点**ゆえ、そちらへ譲る。**他に2件、単位が問われる箇所がある。**

| 件 | 1回のUndoで戻る範囲 | 直感と合うか |
|---|---|---|
| **削除（2-2）** | 要素＋機器表エントリ | **合う**（D5で測る） |
| **機器名（2-3のN3）** | **同名の全要素＋機器表のキー移行** | **合う**（1回のリネーム操作＝1回のUndo。N3で測る） |
| **配置＋合流先（3節）** | **裁定次第** | **要裁定** |

**「戻る単位が使い手の直感と合うか」は、テストでは「Undoを何回押せば操作前か」で測れる。**
**アサーションは`vm.UndoCommand.Execute(null)`を1回だけ呼んで期待状態を確かめる形にする**
——**2回押さねば戻らぬなら、その1回目で落ちる。**

## 6.【DoD 5】PR-27の点検——退化入力で検出力が消えぬか

**本設計で意図的に避けた入力を、理由とともに明示する。**

| 罠 | なぜ危ういか | 本設計での回避 |
|---|---|---|
| **`GridPos(0,0)`だけで測る** | **行と列を取り違えても通る**（対称） | **`GridPos(1,3)`のような非対称を既定とする**。原点は境界値テストでのみ使う |
| **`GridPos(2,2)`のような対角** | 同上 | 同上 |
| **要素1件だけで測る** | **`Count`の0↔1は戻ったように見えるが、中身の一致は見ておらぬ** | **C3で`Id`・`Pos`・`PartId`・`DeviceName`まで見る**。N3・N6は**2件以上**を用意 |
| **同名の機器名で往復**（`A→B→A`） | **見た目が元に戻るゆえ「戻った」と誤認しうる**（実際は履歴が2つ） | **N4（同値）とN3（別名）を分けて持つ**。往復は使わぬ |
| **空のシートで配置→Undo** | `Count`0↔1のみで、**機器表の戻りが見えぬ** | **P2で`Devices.ByName`も見る** |
| **同じ位置に同じ種別を置き直す** | **`Id`が違うのに見た目が同じ** | **D2で`Id`一致を見る** |

**【最重要・侍への申し送り】上表は「気をつけよ」では効かぬ。**
**`P2`・`C3`・`D2`のアサーションに`Id`・`Pos`を実際に書き込むこと**——
**T-068増分3-b3の轍**（**侍が罠を正しく見立てておりながら、テストの入力値に落とし込めなかった**、
`pattern-recurrence-log.md` PR-27）**を踏まぬため。**

**検出力の実測を勧める**——**`RecordSnapshot`を同値ガードより前へ移す**、
**`Pos`の行と列を入れ替える**等の改変でREDになるかを1度確かめれば、網が効くと確かめられる。
