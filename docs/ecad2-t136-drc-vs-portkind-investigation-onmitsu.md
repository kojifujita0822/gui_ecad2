# 殿のご下問「組み込み図形は現在DRCで判定できているのでは？」への回答（隠密）

調査日: 2026-08-02　調査者: 隠密（key=1785632944373）　依頼元: 家老（T-136）

## 0. 結論

**判定できており申さぬ。** **しかも——DRCは誤りを検出せぬだけでなく、誤りを隠す方向に働き申す。**

**根拠の骨子（すべて一次ソースで確認）**

1. **DRCの診断は10種。うち接続点（`PortDef`）を直接見るものは0件**——すべて`Component`（機器）か`Netlist`（節点）を見る
2. **接続点→Netlistの変換（`NetlistBuilder`）で、母線接続は「位置」だけで決まる**——
   `leftBoundary == 0`／`rightBoundary == columns`（`:160-161`）。**`CreatesComponent`の関門は無い**
3. **三相モータは`CreatesComponent=false`ゆえ`Component`にならぬが、母線unionと横配線には参加する**
4. **結果、非シミュレート記号が配線の中継点として働き、他の要素を母線へ繋ぎうる**
5. **DRCは「母線へ到達できる」と見て警告を出さぬ**——**誤った接続が、DRCを黙らせる**

**ゆえに接続点の種類は、DRCと重複いたし申さぬ。層が違う。**

```
接続点(PortDef) → [NetlistBuilder] → Netlist(節点・Component) → [DRC] → 診断
     ↑ 種類はここ                                                    ↑ DRCはここ
```

**DRCは「でき上がった回路の検査」、接続点の種類は「回路をどう組むかの入力」にござる。**
**上流が誤れば、下流は誤った前提の上で正しく働く——すなわち誤りを見逃す。**

## 1. DoD1: 現在のDRCは組込み部品の接続点をどう判定しておるか

### 1.1 **判定しておらぬ。接続点を見る検査が一つも無い**

`DesignRuleCheck.cs`の診断コードを全て数え上げ申した（**再現手段**＝同ファイルの`public const string`を数える）。

| # | コード | 検査対象 | 接続点を見るか |
|---|---|---|---|
| 1 | `DRC-XREF-001` 駆動元不明 | 機器名と`ComponentKind` | **見ぬ** |
| 2 | `DRC-XREF-002` 死にリレー | 同上 | **見ぬ** |
| 3 | `DRC-XREF-003` 接点数超過 | 同上 | **見ぬ** |
| 4 | `DRC-TYPE-001` 励磁系と入力系の混在 | 機器名と種別 | **見ぬ** |
| 5 | `DRC-TYPE-002` コイルと接点種別の不整合 | 同上 | **見ぬ** |
| 6 | `DRC-CONN-001` ドット無し交差 | `Netlist.VerticalCrossings` | **見ぬ**（Netlist経由） |
| 7 | `DRC-LOAD-001` 左母線から到達不可 | `Netlist`のBFS | **見ぬ**（Netlist経由） |
| 8 | `DRC-LOAD-002` 右母線から到達不可 | 同上 | **見ぬ**（Netlist経由） |
| 9 | `DRC-LOAD-003` 二重コイル | 同上 | **見ぬ**（Netlist経由） |
| 10 | `DRC-PART-001` 部品参照の未解決 | `PartId`の解決可否 | **見ぬ** |

**10件すべてが`Component`（機器）または`Netlist`（節点）を入力とする。**
**`PortDef`を直接参照する検査は一つも無い。**

### 1.2 **なぜそうなっておるか——接続点は既に潰されておるゆえ**

`NetlistBuilder`が接続点を節点（`Node`）へ変換し、`Component`を組み立てる。
**DRCが受け取る頃には、接続点は「どのポートだったか」を失うており申す。**

**すなわちDRCは接続点を判定していないのではなく、判定しようがない位置にある。**

## 2. DoD2: 「判定できておる」と言えるのか——起票時の実測との関係

### 2.1 **台帳の実測を、某の手で再現いたし申した**

**転記でなく再現にござる**（`onmitsu.md`「過去の調査書から数字を引くときは必ず一次ソースで再現」）。

| 経路 | 行 | 実装 | `CreatesComponent` |
|---|---|---|---|
| ノード生成 | `:144-145` | `foreach (var p in ports) Node(...)` | **効かぬ** |
| **母線への直接union** | **`:160-161`** | `if (leftBoundary[i] == 0) unions.Add((leftNode[i], leftRail));` | **効かぬ** |
| Passthroughの左右union | `:165-167` | `if (PartResolver.CreatesComponent(e, parts) && ...)` | 効く |
| 行索引 | `:179` | `if (!hasPorts[i]) continue;` | **効かぬ** |
| **横配線の結合・左母線** | **`:212-216`** | `LeftRailReached(...)`と`severed(...)`のみ | **効かぬ** |
| 右母線自動接続 | `:233` | `&& PartResolver.CreatesComponent(elements[last], parts)` | 効く |
| Component生成 | `:307` | `if (!PartResolver.CreatesComponent(e, parts)) continue;` | 効く |

**7経路のうち効くのは3つ（`:165-167`／`:233`／`:307`）、効かぬのが4つ。**
**台帳は「2つしか守っておらぬ」と記すが、某の数え直しでは3つにござる**——
**`:165-167`（Passthroughの左右union）を台帳は「効く」と正しく記しながら、
本文の要約で「2つ」と書いておった。** **表と文の食い違いにて、表の側が正しい。**

### 2.2 **【核心】三相モータは「Componentにならぬのに、母線へは繋がる」**

**`ElementCatalog.cs:60-64`＝モータの接続点は3つ**
```csharp
ElementKind.Motor => new[]
{
    new PortDef("U", 0, 0),
    new PortDef("V", 0, 1),
    new PortDef("W", 0, 2),
},
```

**`NetlistBuilder.cs:307`のコメントが、モータを名指ししており申す**
```csharp
if (!PartResolver.CreatesComponent(e, parts)) continue;   // 記号のみ(三相モータ・非シミュ自作)は評価対象外
```

**すなわちモータは`CreatesComponent=false`。** **されど——**

| 段階 | モータはどうなるか |
|---|---|
| `:141` ポート0個の除外 | **通過する**（3ポートあるゆえ`hasPorts=true`） |
| `:160-161` 母線への直接union | **参加する**（`CreatesComponent`を見ぬゆえ、U が列0なら左母線へ、W が右端なら右母線へ） |
| `:179` 行索引 | **載る**（`hasPorts`のみで判定） |
| `:212-216` 横配線の結合 | **参加する**（同じ行の隣接要素と結線される） |
| `:307` Component生成 | **除外される**（ここで初めて効く） |

**すなわちモータは「電気素子としては存在せぬのに、配線の中継点としては働く」。**

### 2.3 **これがDRCを黙らせる**

**`CheckLoadReachability`（P8、`:192-219`）は`net.Components`を回し、負荷が母線へ到達できるかをBFSで判定する。**
**モータは`Component`でないゆえ、検査の対象にすらならぬ。**

**されどモータが横配線に参加して母線へ繋いだ結果、
「本来は母線へ届かぬはずの負荷」が届いてしまえば——`DRC-LOAD-001/002`は出ぬ。**

**すなわち誤った接続は、DRCに「異常なし」と言わせる。**
**これが殿の起票時の御言葉「原本でもDRCが正常に機能せず」の、ecad2における形にござる。**

## 3. DoD3: 接続点の種類は何を新たにもたらすか——**重複ではない**

**重複いたし申さぬ。上流と下流にござる。**

| | 見るもの | 決めること |
|---|---|---|
| **接続点の種類** | 部品の宣言 | **その点を母線へ繋ぐか** |
| **DRC** | でき上がったNetlist | **回路として筋が通っておるか** |

**現状、母線へ繋ぐか否かを決めておるのは「位置」ただ一つにござる**（`leftBoundary == 0`／`rightBoundary == columns`）。
**部品の側に「この点は電源に繋ぐ／繋がぬ」を言う手立てが無い。**

**接続点の種類が入れば、`:160-161`が「位置」でなく「意味」で判定できるようになり申す。**
**これはDRCの重複ではなく、DRCの入力を正しくするものにござる。**

### 3.1 **【重要な申し送り】種類を付けるだけでは、何も変わり申さぬ**

**T-136(B)増分4で`PortKind`は既に入り申した。されど`Element.cs`の宣言に明記されておるとおり——**
> **【射程】本増分では見た目のみが対象——`NetlistBuilder`等の接続処理へは反映しない**

**すなわち今は「色が変わるだけ」にござる。**
**`NetlistBuilder`が`Kind`を見るようにして初めて、上記の効きが生じ申す**
（殿裁定2026-07-28(5)「接続方法は別途設計する」に相当）。

## 4. DoD4: 判定できておらぬなら、どこが欠けておるのか

**欠けておるのは「接続点の意図」を表す情報そのもの、およびそれを見る経路にござる。**

| 欠けているもの | 現状 | T-136での手当て |
|---|---|---|
| **接続点が意図を持つこと** | `PortDef`は`Name`/`RowOffset`/`BoundaryOffset`のみだった | **増分4で`Kind`が入った**（見た目のみ） |
| **`NetlistBuilder`が意図を見ること** | **位置だけで判定** | **未着手**（殿裁定＝別途設計） |
| **`CreatesComponent`の関門が全経路に効くこと** | **7経路中3つのみ** | **未着手**（T-136の射程外と見る） |

**この3つ目が、殿のご下問に最も近い箇所にござる**——
**「非シミュレート」という宣言が既にありながら、それが配線を止めておらぬ。**
**接続点の種類を入れても、`:160-161`が種類を見ねば、同じ穴が残り申す。**

## 6. 事実と推測の峻別

**事実（一次ソースで確認）**
- DRCの診断10種と、その入力（`DesignRuleCheck.cs`全文）
- `NetlistBuilder`の7経路と`CreatesComponent`の有無（`:141`/`:144-145`/`:160-161`/`:165-167`/`:179`/`:212-216`/`:233`/`:307`）
- モータの3ポート定義（`ElementCatalog.cs:60-64`）と、`:307`のコメントがモータを名指ししておること
- `PartResolver.CreatesComponent`の実装（`:29-34`）
- **台帳の実測の再現。ただし「2つ」は「3つ」が正**（§2.1）

**推測・未確認**
- **「モータ経由で他の要素が母線へ繋がる」は構造からの推論にて、実測しており申さぬ**——
  **テストで確かめられる形にござる**（モータを列0に置き、同じ行に負荷を置いて`CheckLoadReachability`が黙るか）。
  **某は実行しておらぬゆえ断じ申さぬ。侍に一本書いていただくのが確実にござる**
- **原本GuiEcadが「中心接続点を左右母線へ引く」かは確かめており申さぬ**（殿の御言葉にあるが、某は原本の`NetlistBuilder`相当を読んでおらぬ）
- **殿が「モータのみ個別」と仰せの理由**（§5）は某の読みにすぎ申さぬ

## 7. 【訂正・2026-08-02、侍の実測`T136CNonSimulatedWiringTests.cs`(8件GREEN)を受けて】要旨2は覆り申した

**結論を訂正いたす。モータは「橋」ではのうて「壁」にござった。**

**実測**
- モータのU(境界0)とW(境界2)は**別ネット**（橋になっておらぬ）
- 対照＝モータ不在なら負荷は両母線へ届く
- モータを配置すると、**モータより奥側(反対の母線)への到達が切れる**——左端配置なら左母線への到達が切れ、
  右端配置なら右母線への到達が切れる(鏡像、`DRC-LOAD-001`/`DRC-LOAD-002`が各1件新たに発生)
- モータはComponentにならぬという前提（§2.2）は実測でも裏付けられた

**機序（一次ソースで再確認）**：`NetlistBuilder.cs:212-216`の横配線結合により、モータの一端（W側とする）は
隣接要素とunionされる。されどモータ自身のU-W間は`:165-167`の`CreatesComponent`条件によりunionされぬ
（モータは`CreatesComponent=false`ゆえこの条件を満たさぬ）。ゆえにモータを跨いだ先の要素は、
モータの反対側の母線へ到達する経路を持たぬ。**モータは「他要素を誤って母線へ繋ぐ橋」ではのうて、
「行内の結線を分断する壁」として働いており申した。**

**なぜ見落としたか（家老への回答）**：§2.1で`:165-167`の`CreatesComponent`条件は表として正しく
洗い出しており（「効く」と明記済み）、**見えておらなんだわけではない**。されど§2.2でモータの
具体的な振る舞いを考察する際、「U(`:160-161`)」「W(`:212-216`)」それぞれの**個別の母線到達経路のみ**を追い、
「U-W間が`:165-167`で結ばれるか」という、**既に己が作った表の該当行を、この具体シナリオへ
突き合わせることをしなんだ**。表を作った時点と、それを使う考察の時点が分離しており、
後者で前者を検算し損のうた。**`onmitsu.md`調査ワークフロー7項「結論を出したら、それを使う作業まで
自分で一歩進めよ」の欠落にござる**——己の作った資料を、己が使い切れなんだ。

**覆らなんだ部分**：要旨1（DRCは接続点を見ぬ）・要旨3（`PortKind`は見た目のみ）・
モータがComponentにならぬという前提（§2.2）は実測で裏付けられ申した。層の構造
（`PortDef`→`NetlistBuilder`→`Netlist`→DRC）そのものは健在にござる。**ただし
「上流の誤りがDRCを黙らせる」という結論は撤回し、「上流の誤りがDRCに誤検出させる」へ改める。**
殿のご下問「組み込み図形は現在DRCで判定できているのでは」への答えは変わらず**「判定できており申さぬ」**
なれど、その中身（見逃すか誤検出するか）は逆であった。
