## 2. 【最重要の設計論点】「同じ箱に乗る」を実装として成り立たせる

**台帳は「T-133の殿裁定4（3極記号は主回路シート限定）もこの箱に乗る」と記す**（`todo.md` T-136節）。
**一方、隠密の調査は「`PartDefinition` へ足したフィールドは3極記号へ原理的に届かぬ。別途要る」と結論する。**

**両者は矛盾せぬ——「箱」を `PartDefinition` と読めば届かぬが、`PartResolver` と読めば届く。**

### 侍の案＝`PartResolver` に解決関数を1つ足す（既存3つと同じ形）

```csharp
// PartResolver.cs — Ports/CreatesComponent/ComponentKind と同型の4つ目
public static SheetAffinity SheetAffinity(ElementInstance e, PartLibrary? lib)
{
    var part = lib?.Get(e.PartId);
    if (part is not null) return part.SheetAffinity;      // 自作パーツ
    return ElementCatalog.SheetAffinity(e.Kind);          // 組込み種別（3極記号はここで主回路用と宣言）
}
```

**これで「一つの枷」として振る舞う**——呼び出し側（`ValidatePlacement`）は**組込みか自作かを知らずに済む**。
**既存の`Ports`／`CreatesComponent`／`ComponentKind` が既にこの形ゆえ、新しい構えを持ち込むわけではない。**

**この案なら、T-133の(f)（3極記号の主回路限定）は`ElementCatalog.SheetAffinity`へ1行書くだけで済み、
別立ての判定を要さぬ。** すなわち**殿の「一つの箱」という物差しが、実装としても成り立つ。**

### 渡し忘れを機械に検出させる

`ValidatePlacement` へ**既定値なしの引数**として足す（`samurai.md`「横展開の漏れは機械に検出させられぬか
先に問う【MUST】」＝T-133増分3で実証済みの作法）。

```csharp
private bool ValidatePlacement(GridPos pos, int cellWidth, int cellHeight, Sheet sheet,
                               SheetAffinity affinity, ElementInstance? exclude = null)
```

**既定値を付けねば、呼び出し元3箇所すべてに手が入る代わり、渡し忘れが原理的に起き得ぬ。**
**とりわけT-133増分4で「Kind経路の配置導線」が新設される際、そこで渡し忘れればコンパイルが通らぬ**——
**本タスクが将来のタスクを守る形になる。**

## 5. 殿へ諮るべき論点（5件）

### 論点1 — シート種別に「どちらでも置ける」を許すか

| 案 | 中身 | 長短 |
|---|---|---|
| **(S-1) 3値**＝どちらでも／制御専用／主回路専用 | **既定＝「どちらでも」** | **既存の組込み15件・自作部品が無改修で従来どおり置ける。** 殿が絞りたいものだけ設定なされば足る。**ただし「設定し忘れ」と「意図してどちらでも」が見分けられぬ** |
| **(S-2) 2値**＝制御専用／主回路専用 | **全部品がどちらかに属す** | **原本GuiEcadのほころびを根から断てる。** ただし**既存の全部品に設定が要る**（殿の手間が増え、増分1で既存テストの前提も広く動く） |

**侍の推奨＝(S-1)**。理由は**段取り**にござる——(S-2)は正しい姿だが、**既存部品すべての設定が揃うまで
使えぬ状態が続く**。(S-1)なら増分1の時点で枷が働き始め、殿は必要なものから順に絞れる。
**(S-2)へ後から寄せることも容易**（既定値を消せばコンパイラが未設定を炙り出す）。

### 論点2 — 枷に反した時の見せ方

**既存パターンは「メニュー・パレットを無効化（予防）＋`ValidatePlacement` で拒否（防御・サイレント）」**。
**侍の推奨＝この前例に倣う。** 理由＝**T-133裁定4で殿が既にこの形を裁可なされておる**ゆえ。
**ただし「なぜ置けぬのか」が使い手に伝わらぬ**という短所があり、**メッセージを出す案もある**。

### 論点3 — 選択リングの色（**家老が「既知の未裁可」と示された件**）

| 案 | 中身 |
|---|---|
| **(R-1) `_theme.Foreground` 流用** | ライト＝黒／ダーク＝明灰。**テーマに自然に馴染み、新しい色を増やさぬ** |
| **(R-2) 新規の意味色** | `DrawingTheme` の意味色枠（`Powered`／`Blue`／`ManualForced`／`Comment`）へ1つ足す。**選択であることが色でも分かる** |

**侍の推奨＝(R-1)**。理由＝**リングは「形」で既に選択を表しており、色に意味を負わせずとも足りる**。
**加えて、赤丸・青丸のいずれの上に重ねても、黒（ライト）・明灰（ダーク）なら埋もれぬ。**
**新しい意味色を足せば、次に色を使いたくなった時の余地がその分狭まる。**

### 論点4 — 接続点の種類に既定値を置くか

**この論点は §2 の作法（渡し忘れを機械に検出させる）と正面から衝突するゆえ、両論を並べる。**

| 案 | 長 | 短 |
|---|---|---|
| **(K-1) 既定値あり** | **既存の27箇所が無改修**。殿裁定(B)2「殿がご自身で設定」とも噛み合う | **設定し忘れが黙って通る**。「既定のまま」と「意図して既定」が見分けられぬ |
| **(K-2) 既定値なし** | **全接続点に設定が要り、漏れが原理的に起き得ぬ** | **27箇所すべてに手が入る**（実装3箇所・テスト11件・組込み5件・ヘルパ2件） |

**侍の推奨＝(K-1)**。理由＝**殿裁定(B)2が「殿がご自身で設定なさる」と定めており、
既定値から殿が変えていく運用が前提**と読めるゆえ。**論点1で(S-1)を推すのと同じ筋**にござる。

### 論点5 — 組込み・テンプレートの種類指定（**殿のお手を煩わせる件**）

**殿裁定(B)2「組み込み・自作の現状のものは殿がご自身で設定なさる」を実行に移すには、
対象の一覧を差し上げる要がござる。**

- **組込み**＝`ElementCatalog.Ports` の3系統（**モータのU/V/W／一般接点のL/R／3極記号は接続点0個ゆえ対象外**）
- **自作テンプレート**＝`BasicPartTemplates` の**16件**。**ただし`TwoPorts()`／`MotorPorts()` の2ヘルパを共有しており、
  このままでは16件が一律に同じ種類になる**（隠密の指摘、侍も共有構造を確認）。
  **テンプレートごとに変えるなら、ヘルパを分けるか引数を足す要がある**

**侍の具申＝増分5の着手前に、対象一覧を表の形で差し上げ、殿にご指定いただく。**
**一律で足りるか、個別に分けるかも併せて伺う。**
