## 2. 設計

### 2.1 `PortKind` enum（新設、`Element.cs`）

```csharp
/// <summary>接続点の種類（殿裁定2026-08-02）。パーツエディタでの見た目（赤丸／青丸）を決める。
/// 本増分では見た目のみが対象——NetlistBuilder等の接続処理へは反映しない（接続方法の設計は別途）。</summary>
public enum PortKind
{
    /// <summary>電源に接続される点（赤）。</summary>
    Power,
    /// <summary>制御配線でDRC無効な点（青）。</summary>
    DrcExempt,
}
```

**命名の理由**——`NonDrc`ではなく`DrcExempt`とした。「DRC対象外」という性質を明確にしつつ、
既存の`SheetAffinity.ControlOnly`と字面が衝突しない（「制御」の語を識別子へ入れると紛らわしいと判じた）。
**意味は上表と一致しており、識別子の選び方自体は家老裁量の範囲**と理解した上での案。

### 2.2 `PortDef`への追加（`Element.cs:41`）

```csharp
public readonly record struct PortDef(string Name, int RowOffset, int BoundaryOffset, PortKind Kind = PortKind.Power);
```

**既定値＝`Power`（論点6、後述）。** 論点4（既に裁可済み＝K-1「既定値あり」）の実装がこれにあたる。

### 2.3 色の決定は純粋関数へ切り出す（`DrawingTheme.cs`）

`samurai.md`「テストしにくいは設計の匂い」に従い、**色を選ぶロジックをView層(`PartEditorCanvas.cs`)に
直書きせず、Core層の純粋関数として切り出す**——テスト可能にするため。

## 3. 論点5（組込み・テンプレートの種類指定）への見立て——**ヘルパ分割は不要**

**依頼された見立て＝「`TwoPorts()`／`MotorPorts()`の2ヘルパが16件（実数15件）を共有しており、
一律で足りるか」。**

**結論＝一律で足りる。ヘルパ分割は不要。**

**理由**
- `TwoPorts()`を使う14件（a接点・b接点・コイル・端子台・セレクトSW・押釦NO/NC・表示灯・タイマ接点各種・
  サーマル・非常停止）は、**いずれもラダー図の行に配置され左右の母線（または連続する横方向配線）へ
  直列に繋がる標準素子**——電気的な性質が同一であり、殿裁定の「電源に接続される点」＝赤に**14件とも
  一律で落ちる**。ヘルパ内で種類を分ける理由が無い
- `MotorPorts()`を使うのは`Motor()`1件のみ——**そもそも共有されておらぬ**（呼び出し箇所が1つしか無い）。
  仮にモータの種類が接点類と異なる（後述、論点8）としても、**共有ヘルパではないゆえ分割の要は生じぬ**
- **ゆえに「分割が要るか否か」は増分4の器の形に影響しない**——`TwoPorts()`／`MotorPorts()`とも
  現状のシグネチャ（引数なし）のまま、内部で`new PortDef(name, row, col)`（第4引数省略＝既定値`Power`）
  を返せば足りる

**【新たに見つけた小論点8・断じておらぬ】モータ（U/V/W）の種類は赤か青か**——**本増分の実装には影響せぬが、
記録しておく**。モータは`Role = PartRole.NonSimulated`で主回路シート専用（見込み、T-136(A)の枷）ゆえ、
「制御配線」ではない。かといって動力線を「電源」と呼べるかも一義には決め難い。**接続処理（NetlistBuilder）が
本増分の対象外である以上、モータの種類も増分4では両論とも実害が無い**——**論点5の対象一覧（増分5）で
殿に諮る際、この点も選択肢として提示するのが筋**と見る。

## 4. 殿へ諮るべき新論点（2件）

### 論点6 — `PortDef.Kind`の既定値はどちらか

| 案 | 中身 | 見え方への影響 |
|---|---|---|
| **(D-1) `Power`（赤）** | **侍の推奨** | 既存の全接続点（27箇所、論点5で個別指定されるまでの間）が**赤**で表示される。§3の見立てどおり大多数（14/15件）が最終的に赤へ落ち着く見込みゆえ、既定と実態の食い違いが少ない |
| (D-2) `DrcExempt`（青） | | 現状の見た目（全ポート青、増分3までの状態）が変わらず維持される。ただし大多数が後で赤へ変わる見込みなら、論点5完了までの間「実態と違う色」が広く表示され続ける |

**侍の推奨＝(D-1)。** 理由＝§3の見立て（14/15件が赤）と整合し、**論点5で殿が個別指定を終えるまでの
「暫定表示」が実態に近い方を選ぶ**。

### 論点7 — 赤の具体的な色調（RGB値）

**青は据え置き**（既存の塗り色`(255,30,144,255)`＝DodgerBlueをそのまま`PortDrcExempt`として流用、
変更コスト・見た目変化とも最小）。**赤は新規に決める要がある**——殿裁定「赤丸」は色相を指すのみで、
具体的な明度・彩度までは指定されておらぬ。

**侍の見立て（案のみ、選定は殿裁可を要す）**
- 案イ＝素朴な赤`(255,0,0)`系
- 案ロ＝既存の選択ストローク`selectedStroke`（OrangeRed、`255,69,0`、`PartEditorCanvas.cs:676`）と
  紛れぬよう、選択リング色（`_theme.Foreground`）・青（DodgerBlue系）のいずれとも十分に離れた赤系を選ぶ
  （**選択はリングという「形」で表すため色の衝突自体は実害が無いはずだが、紛れにくいに越したことはない**）

**具体の値は実装着手時にサンプルをお見せして殿裁可を仰ぐのが筋**（論点3・選択リング色の前例に倣う）。

   落ちる（例＝暗い赤が沈む）場合は増分3の選択リングと同様、実機確認後に手当てが要りうる**
4. **§1「16件→15件」の事実訂正は増分4の実装量に影響しない**（対象一覧の件数は増分5の話）が、
