# T-145 縦ずれ手当て(VAlign.Middle化) 静的レビュー(隠密)

対象コミット a7fcb15。深度は軽量既定、DoD整合と新規テストの検出力に絞る。とりわけ「着手前確認がそのまま検分の軸になる」との采配どおり、残差の数・向きが実装・報告と食い違わないかを重点で見た。

## 結論

修正の方向・仕組みそのものは妥当。射程(モータのみ)も正しく塞がれ、RED証明の件数も実ファイルと一致する。ただし残差の数値について、侍の報告(三箇所に明記)のうち一箇所は実在せず、数値の範囲にも独自計測との食い違いが一点ある。実害(コードの不具合)ではなく報告の精度の問題だが、家老の采配どおり指摘する。

## 1. DoD整合(モータのみVAlign.Middleへ、DefaultLabelDy/Dxは幾何値のまま)

`DiagramRenderer.cs`の差分を確認。新設した`DeviceNameStyle(ElementKind labelKind)`は`labelKind == ElementKind.Motor`の時のみ`VAlign.Middle`を返し、他は元の`VAlign.Bottom`のまま(`_theme.Text(TextRole.DeviceName)`をそのまま返す)。呼び出し箇所(`DrawElementLabel`内)も1箇所のみで、他の描画経路(コメント・タイマ種別ミニラベル等)には影響していない。

`ElementCatalog.cs`は本コミットで一切変更されていない(`git show a7fcb15 --stat`で確認)。DefaultLabelDy/Dxが幾何値のまま据え置かれているという申告は正確。

前例(ランプ色ラベルが既にVAlign.Middleを使っている)も一次ソースで確認した。`DiagramRenderer.cs:1060-1068`(表示灯の中央にランプ色を記入する箇所)が`VAlign.Middle`を明示しており、申告どおり存在する。

## 2. 新規テストの検出力

追加された3つのテストメソッドの実ケース数を数え直した。

| テストメソッド | ケース数 |
|---|---|
| モータの名は中央揃えで描かれる(Theory) | 2 (PartId経路・Kind経路) |
| モータ以外の名は下端揃えのまま(Theory) | 4 (Coil/ContactNO/Lamp/Terminal) |
| 揃え方を変えても座標は大円の中心を指す(Fact) | 1 |

合計7件。既存26件+7件=33件で、コミットメッセージの「テスト7件追加(計33件)」と一致する。

RED証明の件数も検分した。改変I(中央揃えを外す、すなわち`DeviceNameStyle`がモータでも`VAlign.Bottom`を返すよう改変)を当てれば、「モータの名は中央揃えで描かれる」の2ケースが落ちるはずで、他のテストは影響を受けない構造になっている。改変J(全種別を中央揃えに、すなわち`DeviceNameStyle`が種別を問わず`VAlign.Middle`を返すよう改変)を当てれば、「モータ以外の名は下端揃えのまま」の4ケースが落ちる。件数(2件・4件)とも実装の分岐構造と一致し、「案3の射程がモータに限られていることの証左」という家老の読みも妥当と判じる。

3つ目のテスト(座標そのものは変わらないことを確認)はVAlignの変更を検出する網ではなく、DefaultLabelDy/Dxが今回いじられていないことを守る別の網であり、改変I・Jのいずれでも通ってよい設計——これは意図された役割分担であり、検出力の欠落ではない。

## 3. 残差の数値・向きの検分(着手前確認が軸になった点)

WpfRenderer.csと同一のFontFamily("Yu Gothic UI")・FontSizeMm(2.0)を使い、既存の使い捨てWPFプロジェクト(前回の調査で作成、リポジトリ外)で、VAlign.Middle使用時の墨の中心とアンカー点(target)のずれを実測し直した。今回はデバイス名として現実的な文字列(大文字ラテン・数字・カタカナ、下降字形は含まない)19種へ広げて測った。

結果、墨の中心はアンカー点より0.0996〜0.1284mm下にずれる(いずれも下方向、侍の「墨が下へ」という向きの申告と一致)。上限の0.1284mmはコミットメッセージ・コード内コメントの上限0.128mmとほぼ一致する。

一方、下限については食い違いがある。侍の申告は0.067〜0.128mm(下端から墨中心まで1.205〜1.263mm)だが、当方の計測では現実的な文字列の範囲でこの下限(0.067mm、墨中心1.263mm相当)を再現できなかった。数字・大文字・カタカナに加え、下降字形を含む文字(g/y/p/q/j)まで試したが、下降字形はむしろ残差を0.33〜0.56mmへ大きく広げる方向に働き、逆側(0.067mmへ近づく方向)には動かなかった。当方の計測範囲では下限は0.0996mm(「Coil」という試験用の文字列でのみ、実際のデバイス名としては使われない綴り)に留まる。

数と向きが実在するかという観点で見ると、コミットメッセージとコード内コメント(`DiagramRenderer.cs:1172-1176`)の2箇所には残差の数値(0.067〜0.128mm)が明記されているが、家老が申告した「三箇所」のうち残る一箇所(テストのdocコメント)には見当たらなかった。`T145MotorLabelOffsetTests.cs`を`0.0`・`0.1`・`1.2`・「残差」で検索した限り、新設テストの doc コメントが言及するのは修正前の症状の大きさ(約1.2mm・忍者実機1.13〜1.16mm・コイルの1.22mm)のみで、修正後に残る0.07〜0.13mmという数値そのものはどこにも書かれていない。

## 4. 見立て(実害の有無)

修正そのもの(VAlign.Middleへの変更、射程をモータのみに絞る設計)は一次ソース・テストとも整合しており、要修正の対象ではない。残差の数値の食い違いは、実装の正しさには関わらない文書上の精度の問題であり、下限0.067mmの出所を侍に確かめてもらうのが筋と判じる(当方の計測が及んでいない文字列・別の測り方をしている可能性がある)。テストのdocコメントに残差数値が無いという指摘は、家老が三箇所と申告した内容の是正として申し送る。

## 再現手段

- DeviceNameStyleの射程確認: `git show a7fcb15 -- src/Ecad2.Core/Rendering/DiagramRenderer.cs`
- ElementCatalog.cs非変更の確認: `git show a7fcb15 --stat`
- テストのdocコメントに残差数値が無いことの確認: `grep -n "0\.0|0\.1|1\.2|残差" tests/Ecad2.Core.Tests/T145MotorLabelOffsetTests.cs`(1.2mm系の記述は修正前症状のみ、0.07〜0.13mmの記述は0件)
- 残差の実測: 前回調査と同じ使い捨てWPFプロジェクトに、デバイス名として現実的な19文字列("M1"〜"M999"・数字・大文字・カタカナ)と下降字形を含む対照群を追加し`dotnet run`で再計測(リポジトリへの書き込みなし)
