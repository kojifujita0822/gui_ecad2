# T-145 縦ずれ(約1.1mm)の原因調査(隠密・独立調査)

前置き。侍の診断は未見のまま本調査に着手した。殿の仮説(円の直径差)と家老の予備測定・留保三点は受け取ったうえで、一次ソースと実測で裁く。

## 結論

原因は円の直径ではなく、機器名ラベルの文字の縦アンカーの取り方(VAlign.Bottom)にある。コイルの0.22mmとモータの約1.1mmは同じ土俵の数ではない。コイルの既定値-5.5はgui_ecadからの移植値(T-007、実図面基準の調整値)であり、WPFのテキストアンカーとは無関係な経緯で決まっていた。モータの既定値-4.5/-20.25はT-145で新規に幾何計算のみから導出した値で、この移植値が結果的に持っていたアンカー分の補正を一切含んでいない。ゆえに片方はアンカーのずれがほぼ相殺され、片方は素通しになった。

## 根拠1: WpfRenderer.DrawTextのVAlign.Bottom実装

`src/Ecad2.Rendering.Wpf/WpfRenderer.cs:98-104`

```
double y = style.VAlign switch
{
    VAlign.Middle => position.Y * K - ft.Height / 2,
    VAlign.Bottom => position.Y * K - ft.Height,
    ...
};
```

機器名ラベルのスタイルは`DrawingTheme.cs:135`で`VAlign.Bottom`、フォントは`Yu Gothic UI`・サイズ2.0mm(`DrawingTheme.cs:92,135`)。`VAlign.Bottom`は`position.Y`(DiagramRendererが計算した"yn")を、FormattedTextの行送り全体(`ft.Height`、字形の実際の高さではなく行送りの箱の高さ)の下端に置く。行送りの箱は字形の実際の墨(インク)より広いため、"yn"を字形の視覚的中心に見立てて計算した式は、実際にはずれる。

## 根拠2: 実測(WPFのFormattedText/BuildGeometryで直接計測)

一次ソースの式(`WpfRenderer.FormattedTextOf`と同一のFontFamily・サイズ)をそのまま使い、独立の使い捨てプロジェクトで直接計測した(再現手段は末尾に記す)。

| 文字列 | ft.Height | 墨の中心(レイアウト原点基準) | VAlign.Bottomアンカー点を0とした墨の中心 |
|---|---|---|---|
| M1 | 2.6599mm | 1.4423mm | -1.2176mm |
| Y001 | 2.6599mm | 1.4545mm | -1.2054mm |
| M2 | 2.6599mm | 1.4462mm | -1.2137mm |
| Coil(参考) | 2.6599mm | 1.4296mm | -1.2303mm |

いずれの文字列でも、VAlign.Bottomのアンカー点(DrawTextに渡すposition.Y)から見て、実際の墨の中心は約1.20〜1.23mm上にある。これはフォント・サイズ・VAlign方式で決まる値で、文字列の内容にはほぼ依存しない(4件とも1.2mm前後で揃う)。

この約1.2mmという大きさは、モータの実機ずれ(横向き約1.13〜1.16mm・縦向き約1.13〜1.15mm)とほぼ一致する。忍者の画素測定(実際のラスタ・アンチエイリアス経由)と、ここでの幾何計測(ベクタのBuildGeometry、ラスタ化前)の間に0.05〜0.1mm程度の差が出るのは、測定方式の違いとして無理のない範囲。

## 根拠3: コイルの-5.5/-5.72の出自(一次ソースで裁く。家老の留保3への回答)

`git log -S "Coil => -5.5"`で辿ると、コイルの-5.5は`6eab0ba`(T-007、gui_ecadからのModel層移植)で導入されていた。コミットメッセージ曰く「namespace変更以外はロジック・コメントとも忠実移植」。コード上のコメントも「密集時の重なり回避の標準位置(実図面の規定図に基づく調整値が由来)」とあり、幾何計算ではなく実図面基準の調整値である。すなわちコイルの-5.5は、ecad2のWPFレンダラのVAlign.Bottomとは無縁の経緯(旧gui_ecad・Win2Dバックエンド)で決まった値を、そのまま移植しただけのものだった。

`e58c2d1`(T-097差し戻し2周目、2026-07-16)で忍者の実機実測により-5.5から-5.72へ0.22mm補正されている。この0.22mmは「-5.5という値がすでに正解に近かった残差」にすぎず、-5.5自体がどれだけアンカー分を含んでいたかは誰も導出していない。

## 根拠4: 数値で裏を取る(コイルの-5.72をアンカー補正から逆算できるか)

モータの導出と同じ幾何(円の中心が行中心=ローカルy=0、`SymbolGlyphs.cs:189`の`C(r,s,cx,cell,0,0,0.420)`)をコイルにも当てはめると、"アンカー抜きの素の幾何値"は横向きモータと同じ-4.5mmになる(円が行中心にある点は共通のため)。ここから根拠2で測ったアンカー分(約1.21〜1.23mm)を差し引くと:

```
-4.5 - 1.21〜1.23 = -5.71〜-5.73
```

忍者が実測で確定させた実際の値は-5.72。素の幾何値からアンカー分をそのまま引いた値と、小数点以下2桁まで一致する。コイルの-5.72は「たまたま近かった移植値+微補正」ではなく、「移植値がすでにアンカー分の大半を(経緯不明のまま)含んでいた」ことの数値的な裏付けと判じる。

## 家老の仮説(円の直径差)への回答

半径比(0.75/0.420≈1.79倍)とずれの比(1.1/0.22=5倍)が合わないという家老の指摘は、円の直径起因説を退ける材料として正しい。加えて、横向きモータ(dy=-4.5)と縦向きモータ(dy=-20.25)でずれの絶対量がほぼ同じ(約1.1mm台で揃う)という実測も、ずれが位置や円の大小に比例しないことを裏付ける。アンカー起因説はこの「位置・大小に依存しない固定量」という実測の性質とも整合する。

## 家老の仮説(テキストアンカー説への反論)への回答

「アンカーが原因なら円の大小と無関係のはずで、コイルもモータも同じ0.22mmになるはず」という指摘には、根拠3・4で答えた。コイルとモータは同じアンカー起因のずれを抱えているが、コイルは移植値が経緯不明のまま大半を打ち消し、モータは新規の幾何式が一切打ち消していない。二つの残差(0.22mmと1.1mm)は同じ量の異なる残り方であり、比較して倍率を論じる対象ではない。

## 殿の仮説(円の直径差)への回答

計測の結果、直径差では説明がつかない。原因はテキストのアンカー(VAlign.Bottom)である。

## 測っていないこと

- 忍者の画素測定と本調査の幾何測定の差(0.05〜0.1mm)そのものの要因(ラスタ化・ヒンティング・アンチエイリアスの寄与分)は測っていない
- 他の既存種別(ContactNO等の-1.5等)も同じ移植の経緯を持つため同種のアンカー分を含んでいる可能性が高いが、実機で不具合が出ていない以上、個別の検算はしていない
- 直し方(VAlign方式の変更か、既定値へアンカー分を織り込むか等)は殿裁定により本調査の範囲外
